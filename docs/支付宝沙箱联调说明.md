# 支付宝沙箱联调说明

更新时间：2026-08-06

## 目的与边界

本文覆盖两条独立支付路径：旅行订单使用支付宝沙箱 WAP 支付跳转；AI 规划会员购买使用本站本地渲染的支付宝预下单二维码。两者均通过支付宝异步通知和服务端主动查询确认真实支付事实。

支付事实只能由服务端验签回调或服务端向支付宝查询后写入。浏览器跳转到返回页不是支付成功证明，不能以 URL 参数、前端状态或手工请求伪造支付成功。

严禁将支付宝应用私钥、支付宝公钥原文、App ID、沙箱买家账号密码、完整回调签名或 `.env` 内容粘贴到本文、Git 提交、日志、截图、工单或聊天记录。私钥仅保留在本机或受管密钥存储中；排障日志只记录订单号、支付流水号、请求 ID 和经脱敏的错误码。

## 当前实现

| 项目 | 当前行为 |
| --- | --- |
| 支付发起 | `POST /api/v1/travel-orders/{order_id}/payments`，仅订单 owner，可接受 `{ "provider": "alipay_sandbox" }`，必须带 `Idempotency-Key`。 |
| 支付宝页面 | 服务端生成 RSA2 签名的 `alipay.trade.wap.pay` HTTPS 跳转地址，前端仅接受 HTTPS 跳转地址。 |
| 异步通知 | `POST /api/v1/payments/alipay/callback`，无需用户登录；服务端限制请求体大小、拒绝重复字段，验签并校验 App ID、商户支付单号和金额。成功时响应纯文本 `success`，否则为 `failure`。 |
| 主动查询 | `POST /api/v1/travel-orders/{order_id}:query-payment`，订单 owner 或平台管理员可调用；服务端调用并验签 `alipay.trade.query` 的响应。 |
| 前端返回页 | 消费端路由 `/payments/alipay/return`。页面只查询仍为 `PAYING/paying` 的本人订单，随后提示到订单页查看。 |
| 幂等处理 | 相同订单和 `Idempotency-Key` 重复发起支付返回同一支付记录；相同支付宝 `trade_no` 的重复通知只结算一次、只产生一条 `payment_record.paid` Outbox 事件。 |

### AI 规划会员购买

| 项目 | 当前行为 |
| --- | --- |
| 创建购买 | `POST /api/v1/membership-purchases`，消费者提交 `{ "membership_plan_id": "<UUID>" }` 和 `Idempotency-Key`。服务端读取已发布、可售计划并快照 CNY 金额、天数及 AI 额度。 |
| 发起二维码 | `POST /api/v1/membership-purchases/{purchase_id}/qr-payments`，仅购买 owner。服务端调用 `alipay.trade.precreate`，响应为 `{attempt_id, payment_no, qr_code, expires_at, status, payment_status, authorization_status}`；消费者端只在本站本地渲染 `qr_code`，不跳转支付宝网页。 |
| 当前二维码 | `GET /api/v1/membership-purchases/{purchase_id}/qr-payments/current`，仅购买 owner。二维码仅在 `pending`/`paying` 且未过期时返回；到期后服务端标记为 `expired`。 |
| 重新生成 | `POST /api/v1/membership-purchases/{purchase_id}/qr-payments:refresh`，仅在当前尝试为 `expired` 或 `closed` 时允许。复用会员购买，创建新的支付尝试和支付单号；旧二维码不会再次返回。 |
| 异步通知 | `POST /api/v1/membership-payments/alipay/callback`。与旅行订单回调相同地限制请求体、拒绝重复字段、验签并绑定 App ID、商户支付单号、金额、交易号和成功交易状态；响应为纯文本 `success` 或 `failure`。 |
| 主动查询 | `POST /api/v1/membership-purchases/{purchase_id}:query-payment`，仅购买 owner。服务端只会采用已验证的 `alipay.trade.query` 支付事实。 |
| 支付页面 | 消费端路由 `/memberships/pay/{purchase_id}`。页面在可见时每三秒查询服务端支付事实，隐藏时暂停、重新可见时立即查询；二维码过期后只允许用户手动重新生成。 |
| 授权 | 每个已支付购买只授权一次：创建一个会员有效期和一个 AI 额度周期，并写入一个 `membership.entitlement_updated` Outbox 事件。再次购买立即生效；已排队未开始的周期自动后移，已支付时间不损失。 |
| 管理重试 | `POST /api/v1/admin/membership-purchases/{purchase_id}:retry-authorization` 仅允许平台管理员对已支付、尚未授权的购买重试；审计读取不返回支付单号、签名、原始回调或渠道交易号。 |

会员购买状态分别表示购买、支付和授权事实：初始为 `pending_payment/pending/pending`；创建二维码尝试后为 `pending_payment/paying/pending`；验证收款后为 `paid/paid/pending`，成功授权后为 `paid/paid/authorized`。单个二维码尝试状态为 `pending`、`paying`、`paid`、`expired`、`closed` 或 `failed`，且有效期固定为十分钟。授权异常可以是 `paid/paid/failed`，随后由管理员重试。重复有效回调或主动查询不会二次延长有效期、创建第二个额度周期或再次发布权益事件。第一期计划为 CNY `19.90`、30 天、10 次完整 AI 行程生成和 300 次 AI 对话；用户没有自助退款接口。

任一必填配置缺失时，适配器明确不可用；发起支付返回 `503` 和 `PAYMENT_NOT_CONFIGURED`，且不创建支付记录、不改变订单状态。密钥或 URL 格式不合法会使适配器构造失败，应先在隔离环境修正配置后再联调，不应尝试通过前端或回调绕过该错误。

## 环境变量

在仓库根目录的本地 `.env` 配置以下全部变量。变量名必须准确，所有值均不得进入文档或日志。

| 变量名 | 用途 |
| --- | --- |
| `ALIPAY_APP_ID` | 支付宝沙箱应用 App ID。 |
| `ALIPAY_APP_PRIVATE_KEY` | 本应用 RSA 私钥，用于 RSA2 请求签名。可为 PEM（换行可写为 `\n`）或标准 Base64 DER。 |
| `ALIPAY_PUBLIC_KEY` | 支付宝公钥，用于验签异步通知和交易查询响应。可为 PEM 或标准 Base64 DER。 |
| `ALIPAY_GATEWAY_URL` | 支付宝沙箱网关地址。 |
| `ALIPAY_NOTIFY_BASE_URL` | 支付宝服务器可访问的 API 公网基地址，不带回调路径。 |
| `ALIPAY_RETURN_BASE_URL` | 付款浏览器可访问的消费端 SPA 公网基地址，不带返回页路径。 |

当前代码固定拼接的地址为：

```text
travel-order notify_url = ${ALIPAY_NOTIFY_BASE_URL}/api/v1/payments/alipay/callback
travel-order return_url = ${ALIPAY_RETURN_BASE_URL}/payments/alipay/return
membership notify_url = ${ALIPAY_NOTIFY_BASE_URL}/api/v1/membership-payments/alipay/callback
```

两个 Base URL 都必须是完整的 `https://` 或 `http://` 地址，且不应包含上述路径或额外路径前缀。会员二维码页不使用支付宝浏览器回跳；旅行订单收银台跳转仍要求 HTTPS。

除支付变量外，后端仍须具备其常规启动配置，例如 `MYSQL_DSN`、`REDIS_URL`、`RABBITMQ_URL`、`ELASTICSEARCH_URL` 和 `JWT_SECRET`。首次联调前应用数据库迁移到包含 `20260806_0021` 的 head：从 `backend` 目录执行 `alembic upgrade head`。

## 公网拓扑与隧道

支付宝服务器访问的是 API 回调，付款完成后的用户浏览器访问的是 SPA 返回页。这是两类不同流量，不能把它们混为一个仅反代 API 的地址。

```text
消费端浏览器
  -> 本地 Vite SPA（例如 http://127.0.0.1:5173）
  -> /api/v1/* 由 Vite proxy 转发到本地 API（http://127.0.0.1:8000）

旅行订单发起支付后
  -> 支付宝沙箱收银台
  -> 支付宝服务器 POST 旅行订单 notify_url
  -> API :8000

旅行订单付款完成后
  -> 用户浏览器 GET 旅行订单 return_url
  -> Vite SPA :5173
  -> 返回页调用同源旅行订单查询接口
  -> Vite proxy -> API :8000

会员购买
  -> 本站 /memberships/pay/{purchase_id} 调用 precreate 并本地渲染二维码
  -> 沙箱 App 扫码付款
  -> 支付宝服务器 POST membership notify_url
  -> 本站页面每三秒调用同源查询接口，收到已付款/授权事实
```

使用 cpolar 或其他公网隧道时，推荐建立两个 HTTPS 公网入口：

| 公网入口 | 本地目标 | 配置变量 | 必须可处理的路径 |
| --- | --- | --- | --- |
| API 隧道 | `http://127.0.0.1:8000` | `ALIPAY_NOTIFY_BASE_URL` | `/api/v1/payments/alipay/callback`、`/api/v1/membership-payments/alipay/callback` |
| 消费端隧道 | `http://127.0.0.1:5173` | `ALIPAY_RETURN_BASE_URL` | `/payments/alipay/return`、`/memberships/pay/{purchase_id}`、SPA 资源和 `/api/v1/*` 开发代理 |

不要把 `ALIPAY_RETURN_BASE_URL` 指向当前 Docker Nginx 的地址。现有 `nginx/nginx.conf` 只将 `/api/` 反代至后端，没有静态文件根目录或 SPA history fallback；请求 `/payments/alipay/return` 会失败。若改用统一公网域名，反向代理必须同时实现：

```text
/api/                         -> API :8000
/payments/alipay/return       -> 消费端 SPA，并回退到 SPA 的 index.html
/memberships/pay/*            -> 消费端 SPA，并回退到 SPA 的 index.html
其他 SPA 路由与静态资源           -> 消费端 SPA
```

在此之前，保持 API 隧道和消费端隧道分离。隧道地址变更后，更新两个 Base URL，重启后端，再重新发起一笔支付；已生成的收银台 URL 不会自动更新。

## 支付宝沙箱控制台配置

1. 在支付宝开放平台沙箱创建或选择与 `ALIPAY_APP_ID` 对应的应用。旅行订单开通手机网站支付（WAP）能力；会员二维码支付开通当面付/预创建订单能力，使用沙箱网关。
2. 在应用密钥配置中上传本应用的公钥，并取得支付宝公钥后填入本机 `ALIPAY_PUBLIC_KEY`。本应用私钥只在本机 `.env` 或密钥管理系统使用，绝不上传、粘贴或记录到文档和日志。
3. 使用支付宝沙箱提供的买家账号完成付款，不使用生产账号或生产网关。
4. 旅行订单的 `alipay.trade.wap.pay` 请求明确传入 `notify_url` 与 `return_url`。会员的 `alipay.trade.precreate` 请求只传入 `notify_url`，返回 `qr_code` 后由本站渲染；不要为会员二维码配置或依赖同步返回地址。
5. 若沙箱控制台当前页面提供支付异步通知地址配置，会员购买填写 API 隧道的 `/api/v1/membership-payments/alipay/callback`。不能填写 `localhost`、私网地址或仅有基地址的地址。

`notify_url` 是支付宝服务器到服务端的 POST，不依赖浏览器登录，也必须能被公网 HTTPS 直接访问。旅行订单的 `return_url` 是支付宝引导用户浏览器回到 SPA 的 GET；会员二维码没有浏览器回跳，二维码、前端倒计时和轮询都不能承担结算职责。

## 联调步骤

1. 启动本地依赖、后端和消费端。后端健康检查应为 `GET http://127.0.0.1:8000/api/v1/health` 返回 `200`；消费端使用默认 Vite 地址或实际配置端口。
2. 启动 API 与消费端两个 HTTPS 公网隧道。确认从外网访问 API 隧道的健康检查可达，并确认消费端隧道访问 `/payments/alipay/return` 返回 SPA 页面而非 404。
3. 在 `.env` 写入六个 `ALIPAY_*` 变量的真实本地值，分别将两个 Base URL 指向当前隧道。不要在终端回显、截图或提交这些值。重启后端使 `Settings` 重新加载。
4. 以消费者身份登录，准备一个当前有效、`availability=available`、金额大于零且币种为 `CNY` 的已有订单。当前供应商适配器仍是不可用实现，不能依赖普通搜索流程生成可支付报价；可使用已有的受控测试订单/报价数据。
5. 在“我的订单”确认初始状态为 `PENDING_CONFIRMATION`、`payment_status=pending`、`fulfillment_status=pending_confirmation`，并点击继续支付。消费端会为同一浏览器会话和同一订单复用 `Idempotency-Key`。
6. 确认支付创建响应为 `201`，包含 `payment_no`、金额、币种、`status=paying` 和 HTTPS `redirect_url`；浏览器随后跳转支付宝沙箱收银台。此时订单应为 `PAYING/paying/pending_confirmation`。
7. 在沙箱收银台用沙箱买家完成付款。观察 API 隧道收到支付宝的异步通知并响应 `success`。不要记录通知的完整表单、`sign` 或密钥材料。
8. 支付宝将浏览器带回消费端的 `/payments/alipay/return`。返回页会查询待处理订单；随后到“我的订单”执行“刷新支付状态”。即使返回页显示完成，也以订单查询结果为准。
9. 期望最终订单为 `PAID_PENDING_FULFILLMENT`、`payment_status=paid`、`fulfillment_status=pending_confirmation`。这只表示收款已确认，尚不表示供应商已确认、出票或履约完成。
10. 若异步通知因隧道短暂不可达而未及时送达，使用订单页刷新或调用查询接口。服务端会向支付宝查询，只有返回已验签、交易成功、商户支付单号与金额均匹配的结果才会结算。

### 会员购买联调步骤

1. 完成前述启动、HTTPS API 隧道和配置检查，并确认 API 隧道能接收 `/api/v1/membership-payments/alipay/callback`。消费者端本地或公网地址应能打开 `/memberships/pay/<purchase UUID>` 的 SPA 页面。
2. 使用平台管理员创建或确认一项已发布且 `purchasable=true` 的 CNY 会员计划，价格 `19.90`、有效期 30 天、生成额度 10、对话额度 300。不要在请求中或界面外伪造购买金额、天数或额度。
3. 以消费者登录并在会员页面选择该计划。确认 `POST /membership-purchases` 仅提交 `membership_plan_id`，其响应为 `pending_payment/pending/pending` 的服务器快照；重复相同购买幂等键应返回同一购买。
4. 点击付款，确认 `POST /membership-purchases/{purchase_id}/qr-payments` 返回十分钟有效的二维码事实。浏览器保持在本站 `/memberships/pay/{purchase_id}`，不得跳转至支付宝网页、也不得请求支付宝静态资源域名。
5. 页面可见时确认其每三秒调用服务端查询；隐藏页面后停止，重新可见后立即查询。用沙箱买家扫码完成付款，观察会员回调返回 `success`，不要捕获或保存完整表单、`sign`、交易号或任何密钥材料。
6. 确认页面无需刷新即变为 `paid/paid/authorized` 并显示有效期。付款前让二维码到期，确认仅在点击“重新生成二维码”后才产生新尝试和二维码；不得以二维码图像、浏览器 URL 或轮询次数判断付款成功。
7. 在会员仍有效时重复完成一笔购买。确认新授权立即生效：`valid_from` 为支付确认时刻（早于当前周期的 `valid_until`），额度立即可用；如存在排队未开始的周期，其开始时间被后移到新周期结束后，已支付时长不变。重放同一笔有效回调应继续返回 `success`，但不能新增授权、额度周期或有效期。
8. 使用会员账户验证 AI 额度：有效会员周期优先使用 10 次完整生成和 300 次对话；额度耗尽返回 `AI_QUOTA_EXHAUSTED`。无有效会员账户则按 UTC 自然月使用 1 次完整生成和 20 次对话，耗尽响应包含升级可用事实。

## 验收与拒绝检查

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 支付发起幂等 | 对同一订单以相同 `Idempotency-Key` 重复请求支付创建接口。 | 两次均为同一支付记录与相同跳转地址；不会创建第二笔支付。 |
| 回调幂等 | 由支付宝重试相同有效 `trade_no` 的通知。 | 两次均返回 `success`；订单保持已支付；仅一条回调事件和一条支付成功 Outbox 事件。 |
| 主动查询 | 在 `PAYING/paying` 时刷新订单支付状态。 | 未支付保持原状态；已支付且签名、单号、金额匹配时结算为 `PAID_PENDING_FULFILLMENT/paid/pending_confirmation`。 |
| 无效签名 | 发送签名错误、缺失或篡改金额的回调。 | 返回 `failure`，不结算；系统保留有限、脱敏的拒绝事实。 |
| 金额/订单不匹配 | 使用其他支付单号或与订单金额不一致的有效格式回调。 | 返回 `failure`，不结算。 |
| 非成功交易状态 | 回调 `trade_status` 不是 `TRADE_SUCCESS` 或 `TRADE_FINISHED`。 | 返回 `failure`，不结算。 |
| 重放到其他订单 | 以已绑定的 `trade_no` 指向另一 `out_trade_no`。 | 返回 `failure`，不结算另一订单。 |
| 权限与参数 | 非 owner 创建支付、缺失 `Idempotency-Key`、provider 非 `alipay_sandbox`。 | 分别为资源隐藏的 `404` 或请求校验 `422`。 |
| 未配置 | 清空任一必填 `ALIPAY_*` 配置后尝试发起支付。 | `503 PAYMENT_NOT_CONFIGURED`，订单与支付记录不变。 |
| 会员回调幂等 | 重发同一会员购买的有效成功回调。 | 两次均返回 `success`；购买和支付保持 `paid`、授权保持 `authorized`，有效期和 AI 额度周期不重复增加。 |
| 会员主动查询 | 在会员购买为 `paying` 时刷新购买状态。 | 未支付保持原事实；只有验签成功、金额和商户支付单号匹配的成功交易才变为 `paid` 并触发一次授权。 |
| 会员二维码到期 | 等待十分钟或受控推进时间。 | 当前尝试为 `expired`，页面停止轮询，不自动创建新尝试。 |
| 会员二维码刷新 | 对 `expired` 或 `closed` 尝试点击重新生成。 | 同一购买获得新的支付单号和十分钟二维码；旧二维码不再通过任何接口返回。 |
| 页面可见性 | 在等待支付时隐藏再显示二维码页面。 | 隐藏时不轮询，显示时立即查询并恢复三秒轮询；已付款、已授权、过期、关闭或失败时不再轮询。 |
| 会员授权重试 | 以管理员身份对已支付但授权失败/待处理购买调用重试。 | 仅该状态允许；成功后创建唯一授权和额度周期。未支付、已授权或普通用户请求被拒绝。 |
| 会员回跳伪造 | 手工修改会员返回页 URL 或直接打开返回页。 | 不创建支付、授权或额度；页面仅显示 owner 可查询到的服务端事实。 |

仅在受隔离的测试环境执行拒绝检查，不要向支付宝生产环境或其他人的订单、支付单号发送请求。

## 已知限制

1. 当前订单读取接口只提供列表和支付查询，不提供订单详情或支付/回调事件查询接口；核对以订单三元状态、请求 ID、受控数据库审计或管理员受限操作视图为准。
2. 当前供应商搜索适配器是不可用实现，真实沙箱支付只能针对已有的有效 CNY 订单联调，不能证明供应商下单、库存锁定、出票或履约确认。
3. 当前实现不含退款发起闭环和供应商履约确认闭环。支付成功只推进至 `PAID_PENDING_FULFILLMENT`。
4. 回调端点仅接受 URL 编码表单，最大 16 KiB、最多 32 个字段，并拒绝重复字段；代理不得改写请求体、字符集或表单字段。
5. cpolar 临时域名的变更会使旧收银台请求携带旧地址。每次变更后都必须更新环境变量、重启 API，并用新订单/新支付发起测试。
6. 旅行订单返回页需要有效的消费者登录态才能查询订单。会员二维码页同样需要登录态；重新登录后重新打开购买二维码页或权益页查询，这不会替代异步通知或服务端查询。
