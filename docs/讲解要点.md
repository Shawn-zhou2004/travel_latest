# 一、工作流的大体流程：

用户提交需求后，接口不会同步等待大模型返回，而是先在 MySQL 中以同一事务创建生成任务和 Outbox 事件。Outbox Publisher 在事务提交后将事件可靠投递到 RabbitMQ。Worker 作为 RabbitMQ 消费者领取任务，并在后台执行 LangGraph 规划工作流。工作流生成的结果先保存为 preview，只有用户确认后才通过行程领域服务写入正式行程。

# 二、总结第二个节点的两个业务流程

langGraph 的流程图上只有 **8 个调度节点**（`validate_request` → `retrieve_evidence` → `planning_agent` → `validate_schema` → `map_agent` → `generation_review_agent` → `save_immutable_preview_with_audit` → `user_confirmation`），但第 2 个节点 `retrieve_evidence` 内部顺序做了两件可独立审计的事：

1. **`memory_retrieval_agent`** —— 加载并过滤当前用户的显式长期偏好（profile 记忆），写一条审计；
2. **`retrieval_agent`** —— 检索公共知识（官方/社区 RAG）与已验证 POI 候选，过滤城市与合规性，准备模型可用的事实来源，写另一条审计。

因此对外讲解、做审计时，常把它们拆成 **9 个业务步骤**，这不是并行或两个图节点，而是同一图节点里的顺序执行。

# 详细：这两个步骤分别是什么

### 第一步：`memory_retrieval_agent`

意思是：读取当前用户自己的旅行偏好。

例如用户之前主动保存过：

```
{
  "budget": {
    "level": "balanced"
  },
  "pace": {
    "value": "slow"
  },
  "diet": {
    "avoid": ["spicy"]
  }
}
```

系统会根据当前登录的 `user_id` 加载这些内容，并再次过滤，确保：

- 只能读取当前用户自己的记忆；
- 已删除记忆不会被使用；
- 结构不合法的记忆不会交给模型；
- 向量索引里旧版本的记忆不会被误用。

对应代码：

[workflow.py](oc://renderer/D:/飞思/周正/the_third_project-v1/backend/app/modules/ai_workflows/workflow.py:530) 中的 `_graph_retrieve_evidence`：

```
await self._load_profile_memory(state)

profile = state.profile_memory
records = _memory_records_from_profile(profile, state.request.user_id)

memory_result = self.memory_retrieval.retrieve(...)
state.profile_memory = _profile_from_memory_records(memory_result.records)
```

这部分处理完成后，系统记录一条审计记录：

```
_record_production_audit(
    state,
    "memory_retrieval_agent",
    ...
)
```

审计信息会说明：

```
加载了多少条用户偏好
最终选中了多少条
是否忽略了不合法或未类型化的记忆
耗时多久
```

------

### 第二步：`retrieval_agent`

意思是：检索公共旅行知识。

例如用户问：

```
“成都三日游，喜欢博物馆和美食”
```

系统会去官方知识域、社区知识域等检索：

```
成都博物馆资料
成都景点资料
成都旅行规则
已审核的 POI 信息
```

然后把可用的知识整理为 citations，也就是来源引用。

对应代码紧接着执行：

[workflow.py](oc://renderer/D:/飞思/周正/the_third_project-v1/backend/app/modules/ai_workflows/workflow.py:555)

```
citations = await self.dependencies.rag_retriever.retrieve(state.request)
documents = tuple(_retrieval_document(citation) for citation in citations)
```

它之后还会：

1. 过滤不符合当前城市的数据；
2. 保留可信、合规的 citation；
3. 准备高德验证过的 POI 候选；
4. 如果候选不足，才走受控 MCP 联网兜底；
5. 最终让模型只能从候选地点中选择。

完成后又记录一条独立审计：

```
_record_production_audit(
    state,
    "retrieval_agent",
    ...
)
```

`state` 可以理解成这次 AI 规划任务贯穿全程的“任务档案”。

其中：


它可能记录成这样：

```
[
  {
    node: "validate_request",
    status: "completed",
    duration_ms: 3
  },
  {
    node: "memory_retrieval_agent",
    status: "completed",
    loaded: 4,
    selected: 3
  },
  {
    node: "retrieval_agent",
```

所以尽管 LangGraph 图上只有一个 `retrieve_evidence` 方块，审计中可以清楚看到：

```
各自取了多少数据
是否发生降级或过滤
```

这就是“可独立审计”的含义。

# 三、`generation_job_id`和workflow_run_id` (trace_id)

| 维度            | `generation_job_id`       | `workflow_run_id` (trace_id) |
| :-------------- | :------------------------ | :--------------------------- |
| 代表            | 业务任务                  | 具体执行尝试                 |
| 变化频率        | 用户不重试则不变          | 每次 Worker 跑都变           |
| checkpoint 隔离 | 共享（续跑）              | 隔离（重新开始）             |
| 适用场景        | Worker 崩溃恢复、中断续跑 | 用户主动重试、并发安全       |

**job_id 是"任务"的身份证（一单一个，从头到尾不变）；thread_id 是"这次图运行"的存档线（一条 run 一条，8 个节点共用这一条）；trace_id 是"这次处理"的追溯号，run_id 就是它，thread_id 又等于它。job_id 变＝换任务；thread_id 变＝这条图运行换了一条全新的状态存档线。**

**当前策略**：

```
有 workflow_run_id -> 用它（隔离，重新开始）
无 workflow_run_id -> 退回 generation_job_id（兼容，续跑
```

# 四、八个节点描述

**节点 1 `validate_request` —— 核单** 先把用户要什么盘清楚：目的地、天数、预算、必须去的景点。这步**不碰任何外部系统，纯校验**，就是"订单别是瞎填的"。天数不能超 7 天、预算不能是负数，缺参数直接报错打回。它保证后面所有工作都建立在一个合法请求上。 ➡️ 它其实不是"生成"的一部分，而是**门槛**——进大门先安检。

**节点 2 `retrieve_evidence` —— 找料（全流程最重的准备）** 把所有给你"排行程的依据"攒齐：用户自己的旅行档案（偏好）＋网上攻略库（官方+社区）＋如果还不够就联网搜兜底。整理成一份"候选景点清单"，而且要**够量**（至少天数×2），少了就失败。 ➡️ 一句话："先喂草料，后面设计师才能干活。"这一节虽然在网上是 Step 2，但内部其实是两小步：**读记忆 → 搜资料**。

## 中段 · 生成三连（节点 3-5）

**节点 3 `planning_agent` —— 起草（唯一的"聪明脑袋"）** 这才是真正调**大模型**的那一下。把前面的资料打包成提示词，让模型**只输出一份结构化的 JSON 行程草案**。加了很多约束：必须用准备清单里的真景点、不能编造、必去景点一个都不能少。 ➡️ 记住：**整条流水线只有这一个节点在"生成内容"**，其余全是检查、搬运、校验。

**节点 4 `validate_schema` —— 校稿** 大模型输出的是"一段文本"，这段规定日期对得上、每天 2-3 个活动、景点都来自清单。**把它从"看着像 JSON"变成"真正合格可用的行程对象"**。格式不对、日期对不上、漏了必去 → 打回重做。 ➡️ 对照：节点 4 是"格式对、结构对"，节点 6 才是"内容对不对"。

**节点 5 `map_agent` —— 踩点** 拿行程里每个景点去**高德二次核验**：这东西是不是真实存在的 POI、实际在哪个城市哪个坐标。防止模型排出"不存在的景点"。核查完的打上坐标，行程就"落了地"。 ➡️ 一句话："大模型负责想，高德负责确认落地。"

## 终段 · 审·存·交（节点 6-8）

**节点 6 `generation_review_agent` —— 终审（唯一会"绕回头"的节点）** 总质检：预算超没超、每站有没有证据支撑、路线顺不顺。**不过就退回去让设计师重排，最多返工 2 次**；重排还不通过就判失败。通过了才允许往下。 ➡️ 面试亮点：**这是 8 个节点里唯一的分流点**（条件路由），其它节点都是顺序往下。"重规划最多 2 次"是个可以主动强调的设计。

**节点 7 `save_immutable_preview_with_audit` —— 存档** 把"最终行程＋引用证据＋每一步干了什么"一起**存成一份不可变的预览快照**，还带完整审计（每一步耗时、用哪个版本）。存后就不能改，保证可追溯。 ➡️ 记住英文难背，就拆着记：`save`(存) `immutable`(不可变) `preview`(预览) `with audit`(带审计)。

**节点 8 `user_confirmation` —— 待批（HITL 停止线）** 到这图就"完成任务"了，但**什么都没写进正式行程表**，只是标记"等用户确认"。真正的落库是用户在你面前点了"确认"之后，再由另一个带身份校验的接口去写。 ➡️ 面试必答：**人和机之间留了一条确认停线**（Human-in-the-loop），AI 胆出草稿，不擅自动用户的正式数据。

## 记忆口诀 & 面试话术

**口诀**：核单 → 找料 → 起草 → 校稿 → 踩点 → 终审 → 存档 → 待批。把它当流水线画面，顺序就锁住了。

**面试口语版（可直接背）**：

> "整个工作流是一个 8 节点的 LangGraph 状态机，像一条流水线：先校验请求合法性（validate），然后检索记忆和攻略凑齐候选景点；接着调一次大模型生成行程 JSON 草稿（planning），再校验它的格式（validate schema），并逐个用高德核验景点真实性（map）。之后进入终审（review），这里是唯一的分流点——不合格就打回重排，最多重试两次；通过后把最终草稿连同审计记录存成不可变预览（immutable preview with audit）。最后停在用户确认（user confirmation），由另一个带权限校验的接口才把方案正式写入。整条链路是异步的，靠幂等键和出库事件保证可安全重试。"

面试官如果追问"为什么只有一个节点调 LLM"——答：**把"聪明"集中在 planning 一步，其余全部用确定性校验（高德、约束检查）把关，可审计、可回溯、不失控**。这是这套受控多智能体设计的核心卖点。

# 五、**图包装满足 LangGraph 的签名契约，核心层保持纯净可测，计时/审计/进度/异常统一收在适配层不透传不丢**。

"我每个图节点都拆成两层：外面 `_graph_xxx` 是图包装，满足 LangGraph 'async 状态dict → 状态dict' 的签名要求，同时集中做计时、生产审计、进度上报；里面 `_user_confirmation` 这类是纯业务方法，只改共享状态、对框架零依赖。这样拆的好处是：核心逻辑能脱离 LangGraph 单独单测；异常按原样抛出，由 worker 按异常类型分流；而每条节点产出和审计记录都能统一落库，保证完整可追溯。"

"我让每个 LangGraph 节点返回同一个外层 dict，里面用一个键 `workflow_state` 装着真正的共享状态对象。节点开头取出来、结尾塞回去，这样既满足 LangGraph 只要 dict 的约束，业务上又能方便地读写同一个对象、保持审计轨迹不丢失。"

# 六、Outbox 面试讲解

## 讲第一个点：为什么事件要先"落库"而不是直接发 MQ

> "核心是**解决一次消息发布的持久性**。如果业务提交成功就立刻发 MQ，万一 MQ 宕机或网络断了，这条消息就丢了。所以我不直接发，而是把事件写进 outbox 表，和业务数据在**同一次事务**里。这样 even broker 挂了，事件也在库里躺着，恢复后再补发——**'业务提交'和'事件不丢'被绑成了原子动作。**"

（这正好回应你之前问的 `broker 挂了也不丢`。）

## 讲第二个点：worker 的"生产者 + 消费者"双角色

> "worker 进程同时扮演两端。作为生产者，它轮询 outbox 里待发的事件，发布到 RabbitMQ；作为消费者，它又订阅 RabbitMQ，把消息派给对应处理器。两端的确认机制是这套可靠性的精髓。"

## 讲第三个点（最该讲清）：两层确认 = 双保险

> "这套系统有两道防重，缺一不可。**第一道**在发件侧：联系人发布时开了 RabbitMQ 的 publisher-confirm，只有 broker 明确回执'收到了'，才把 this event 的 `published_at` 标记上；发布器只捞 `published_at IS NULL` 的行，所以已确认发过的不会再发。**第二道**在收件侧：MQ 是至少一次投递，可能重复，所以每个消费者处理前先往一张 `ProcessedEvent` 幂等表插一条 `(consumer, event)` 记录，这个插入和业务逻辑在**同一个事务**里——成功了才给 MQ 回 ack，重复投递会因为唯一约束直接跳过。两道一前一后，把'重复发'和'重复执行'都挡住了。"

## 一句话收尾（留给你的制高点）

> "所以整条可靠性就是一句话：**一次事务写库 + 发布确认标记已发 + 幂等表同事务确认已消费。** 生产端挡多发，消费端挡重复，共同实现'至少一次、但不重复'。"

# 七、存储 + 检索

"RAG 分存储和检索两段。存储段：运营侧知识的审核/发布通过后，写一条 outbox 事件，worker 异步收到后调 KnowledgeIngestionService.ingest——先把整篇知识按 800 字符切成无重叠的小块，逐块用 embedding 编码，再各写两份投影：向量进 Milvus（稠密检索用）、原文进 Elasticsearch（BM25 用），每块带 chunk_id（文档id+块序+内容哈希）保证可追溯、内容一变引用即失效。 检索段：用用户输入 + 城市 + 过滤条件做混合检索——prompt 编码成向量，Milvus 稠密和 ES BM25 两条路并行各取 20，再用 RRF（按排名代数加权）去重融合成 top-8，过一遍 min_score 置信门槛，太低宁缺毋滥。整个过程按官方/社区双域切库：官方证据必须命中否则判依赖故障，社区证据尽力而为，而且存储层过滤就只召回同城、公开、已审核的块。拿到的引用再经受控同城过滤、逐 POI 高德核验，凑满 2×天数（不够联网兜底）成为已验证候选，才喂给 planning 生成行程。"

# 八、 AI 智能助手的整体流程

**1. 受理与鉴权。** 用户在 AI 助手页选中一个对话，输入一段文字点发送。前端不等待，先把用户消息和一版空回答"乐观地"渲染上来，同时生成一个随机的 `client_message_id` 作为本次提问的身份证，通过 SSE 长连接发到 `POST /ai/conversations/{id}:ask-stream`。后端校验消费者登录态后，按 `client_message_id` 查重：如果是重试就复用旧任务，不重复扣权益；是全新问题才扣一次 AI 权益并建立一条运行记录（run）。

**2. 意图分类（不花钱、不耗时）。** 后端不调模型，只用正则把问题归为三类：寒暄/闲聊 → 直接聊；含旅行关键词 → 走"查官方资料"；同时含实时词（价格、天气、营业时间…）且含旅行词 → 走"查官方资料，不够再联网"。这一步决定后面走哪条路。

**3. 官方检索（核心找料）。** 对旅行类问题，后端打开 AI 运行时，只检索**官方审核知识域**（不碰社区和个人记忆），拿到引用条目。随后做一道相关性校验——把问题开头提到的目的地和检索片段比对，防"全局 RAG 误命中"，剔除看着相关实则无关的片段。命中了就进入生成；没命中、或是实时类问题，就进入下一步联网兜底。

**4. 联网兜底（受控、临时、一次性）。** 只有"实时问题 + 官方不足"才触发。后端用 MCP 调 WebSearch 搜到一批网页，按规则打分排序（官方域名、景点关键词、时效性加权），并发抓取前 5 个页面的正文，切成临时引用块，标记为 `live_web`。**参数由后端固定，不让模型自由决定调用什么**；抓到的内容只存在本次回答的引用里，不写进公共知识库。若连联网也没结果，直接给澄清文案。

**5. 来源约束生成（答案从这里来）。** 把"当前问题 + 引用资料"交给一个受约束的模型，system prompt 明确"只依据传入来源回答，不得编造价格/时间/地点"。生成时逐段通过 `delta` 事件流式推给前端，用户能看到一句一句"打出来"。若模型失败但有引用，用引用摘要拼一个退化回复兜底，保证永远有据可依。

**6. 落库。** 回答完成后，把完整消息（含文本 + 引用 + 类型）写进 PostgreSQL，run 状态置为 `completed`，把最终消息作为 `completed` 事件推给前端，替换掉临时的空气泡。此时整段对话历史持久化，刷新也能看到。

**7. 断线可恢复。** 因为 run 全程持久化，前端若在流中途断线，可用 runId 调重放接口把已完成/失败的状态取回来，或重新拉一遍消息列表兜底，不会卡在半截。

**行程生成复杂到值得用 LangGraph（所以用了）；AI 助手简单到连框架封装都不用，直接手写。按复杂度选型，不为了用框架而用框架。**

# 十、三个状态分别是什么意思

关键点：**run 不是被后台 Worker 消费的 MQ 队列，而是在你那个 SSE HTTP 请求里，由后端代码当场即时推进的**。流程是：

1. **创建（queued）**：前端 `POST /ask-stream` 进来，后端按 `client_message_id` 查重。若这条提问第一次出现 → 先写入一条 user 消息，再 INSERT 一条 run，初始状态 `queued`。若重复提问 → 直接复用已有 run，不重复建、不重复扣权益。
2. **认领（queued → running）**：后端调用 `start_assistant_run`，执行一条**带条件的更新**：`SET status='running' WHERE id=? AND status='queued'`。因为只有 `queued` 才能转 `running`，就算多个请求同时进来，也只有一个能"抢"到更新成功，其余返回空、被挡在外面——**这就防住了并发重复执行**。所以 `running` 的含义是"有个执行方占住这把锁开始干活了"。
3. **干活 + 归档（running → completed）**：后面的检索、联网、生成、SSE 流式推送全在这一个请求里顺序执行。答完后调用 `complete_assistant_run`：`FOR UPDATE` 锁住该行，写入 assistant 消息（幂等键 `client_message_id:assistant`），再把 run 置为 `completed`、记上 `assistant_message_id` 和 `completed_at`，把完整消息作为 `completed` 事件推给前端。
4. **中途失败**：任一环节抛错 → `fail_assistant_run` 把 run 置 `failed`，记录 `error_code`/`error_message`，释放权益，推 `failed` 事件。

## 存在哪：一张表 + 两条消息记录

- **表**：PostgreSQL（`ai_postgres_dsn`，非 MySQL）的 `ai_assistant_runs`。
- 它不存回答内容本身，存的是**这次 run 的进展和指向**：`user_message_id`（指向 user 消息）、`assistant_message_id`（指向 assistant 消息）、`status`、`source_mode`、`error_code/message` 和时间戳。
- 真正的**问题/回答文本 + 引用**存在 `ai_messages` 表（`content` JSONB），run 通过外键指向它们。会话归属在 `ai_conversations`。



# 十一、中断恢复整个图

## 第一道闸：认领时——行锁 + 只认 queued（拦截“同时来两张纸条”）

`start_attempt`（service.py:172-179）：

```python
job = await self.session.scalar(
    select(GenerationJob).where(GenerationJob.id == job_id).with_for_update()
)
if job.status != "queued":
    return None          # 别人已认领/已终态 → 直接放弃，不执行
job.status = "understanding"
```

- `with_for_update()` 给这一行**加行锁**（数据库层互斥，同时只有一个人能拿到锁改这一行）。
- 锁里看 `status`：**只要不是 queued 就返回 `None`**。
- 所以同一 `job_id` 被 broker 重复投递时：第一张纸条抢到锁 → 改 queued→understanding → commit；第二张纸条进来拿锁一看 status 已是 understanding → 返回 None → **图不跑第二遍**。

> 类比：同一件衣服(行)一次只有一个人能套上去量（改状态），第二个店员来拿时衣服已经被人穿走了。

## 第二道闸：写进度时——trace_id 对账（拦截“旧纸条迟到回写”）

上面防的是“重复投递跑两遍”，但还有个更刁钻的：**第一张纸条其实没死，只是慢了**。broker 超时又投了第二张，第二张抢到认领并把 `trace_id` 换成了新 id（service.py:181）。

此时第一张纸条终于跑完回来写进度——如果不拦，就会把第二张的新进度覆盖掉。所以 `mark_progress` 对账（service.py:210）：

```python
if job.trace_id != trace_id:
    return None          # 当前认领者不是我 → 我这张是旧投递，拒绝回写
```

> 类比：工牌(trace_id)每次认领就换新。旧员工迟到回来打卡，保安一看他的工牌不是现在的 → 不让他打。

## 一句话串起来

> **防“多跑”靠行锁认领（只认 queued），防“乱写”靠 trace_id 对账——前者保证只执行一次，后者保证只有当前这次投递能回写进度。**
