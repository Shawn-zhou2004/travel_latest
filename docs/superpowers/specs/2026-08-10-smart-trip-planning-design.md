# 智能旅行规划入口设计

## 目标

将消费者端 `/plan` 从面向验收的 AI 请求表单升级为面向普通用户的旅行规划入口。用户通过目的地、日期、偏好和可选补充想法启动手动或智能规划，不需要了解行政区划代码、RAG、MCP 或 POI ID。

## 范围

本设计包含以下能力：

- 目的地联想、标准结果选择和城市代码归一化。
- 日期范围与旅行偏好收集。
- 手动规划的空白日期骨架创建。
- 智能规划的已审核知识优先、实时 MCP 网络检索兜底、POI 验证、预览和确认写入。
- 当前预览临时网络来源与长期审核知识的隔离。

本设计不包含支付、库存、供应商履约、图片识别、网页全文爬取或将实时网络来源自动写入长期知识库。

## 用户界面

`/plan` 显示以下输入与操作，移除“目的地行政区划代码”输入框：

1. 目的地搜索框。
2. 开始日期和结束日期选择器，自动显示连续旅行天数。
3. 最多三个旅行偏好标签：`经典必玩`、`吃吃喝喝`、`小众探索`、`拍照出片`、`逛街购物`、`citywalk`、`自然风光`、`文艺展览`、`历史古建`。
4. 可选“补充想法”自由文本框。
5. `手动规划` 与 `智能规划` 两个操作按钮。

不实现推荐行程卡片。

### 目的地联想

输入框采用防抖查询，并展示可选择的标准地点项。每项显示显著主名称和次要完整层级地址，例如：

```text
长沙市
中国 · 湖南省 · 长沙市

长沙县
中国 · 湖南省 · 长沙市 · 长沙县

长春市
中国 · 吉林省 · 长春市
```

查询结果使用高德地点或行政区划搜索服务，保存高德标准名称、完整层级地址和归一化 `city_code`。排序规则为：

1. 完全匹配结果。
2. 名称前缀匹配结果。
3. 其他相似名称结果。

用户必须从下拉结果确认目的地，手工输入但未选择的文本不可提交。下拉支持鼠标选择、上/下方向键切换和回车确认。未找到结果时显示明确空状态，不调用 AI。

区县或景区结果必须归一到其所属城市 `city_code`。界面保留用户选中的地点名称和完整地址，检索、POI 校验及跨城隔离一律使用归一化后的城市代码。

### 日期和偏好

日期范围必须为连续一至七天，不能选择过去日期或结束日期早于开始日期。页面自动显示总天数。

偏好标签使用多选，最多三项。标签作为结构化 `preference_tags` 传给后端，不能通过拼接提示词替代。补充想法始终可选，允许任意自然语言，例如陪同人群、节奏、忌讳和特殊需求。

### 两种规划方式

`手动规划` 创建仅含日期骨架的私有行程，随后进入工作区。该路径不调用 MCP、RAG、LLM 或 Worker，因此 AI 依赖不可用时仍可完成。

`智能规划` 创建异步 generation job，并在用户确认预览前不创建或修改正式行程。按钮在以下条件满足前禁用：已确认目的地、有效日期范围、选择不超过三项偏好。

## 智能规划数据流

智能规划请求保存以下不可变快照：标准目的地名称、完整地址、归一化城市代码、日期范围、偏好标签和补充想法。

```text
用户请求
  -> 城市结果已确认
  -> 已审核知识检索
  -> 候选不足时实时 WebSearch MCP
  -> 临时来源候选 JSON 归一化
  -> 高德 POI 查询和同城验证
  -> 规划 Agent
  -> 路线、日期、数量、来源校验
  -> 不可变预览
  -> 用户确认
  -> 版本化写入正式行程
```

### 资料来源

检索 Agent 先查询当前城市的已审核长期 RAG 知识。当已验证候选不足以支撑规划时，才调用 WebSearch MCP。

MCP 搜索结果仅作为当前 generation job 的临时来源。它们不自动写入 Milvus、Elasticsearch 或长期 RAG。管理员审核并明确批准后，才可走既有知识治理和索引流程。

实时网络候选必须归一为受控 JSON，至少包含：候选名称、来源 URL、来源摘要、偏好匹配原因和来源类型。规划 Agent 不能访问网页原文，只能接收已验证候选 JSON。

每个候选必须经高德解析或验证获得真实 `poi_id`、标准名称、坐标和行政区划。没有 `poi_id`、不属于目标城市、来源缺失或与其他候选重复的地点必须剔除。规划 Agent 不能自行编造 `poi_id` 或地点事实。

### 规划与校验

系统默认目标为每日三个地点。每个预览日必须有至少两个已验证地点；如果只能支持两个地点，预览需明确说明“当前资料仅支持每日两个已验证地点”。少于两个地点时，智能规划不生成预览。

规划与复核必须校验：

- 日期完整、顺序正确，且在用户选择范围内。
- 每日地点数满足两至三个的可验证范围。
- 所有 POI 属于目标城市。
- 同一 POI 不重复出现。
- 路线顺序与行程地点顺序一致。
- 每个地点具有至少一个审核知识或临时实时来源 citation。

预览展示每个地点、路线和引用，并标识引用是“平台已审核资料”还是“本次实时网络资料”。用户确认前，任何正式行程版本不得被创建或修改。

## 任务状态与失败处理

generation job 的用户可见处理阶段为：

```text
queued
-> resolving_destination
-> retrieving_reviewed_sources
-> searching_live_sources
-> verifying_pois
-> planning
-> validating
-> awaiting_confirmation
```

`searching_live_sources` 只在已审核资料不足时出现。

- 城市未确认或不可归一：前端阻止提交，并要求从结果中选择目的地。
- 已审核资料与实时网络资料均不足：任务以 `no_result` 完成，提示“未找到足够可验证的地点”，提供调整偏好和手动规划入口。
- MCP、模型、高德、Milvus、Elasticsearch 或队列异常：任务以 `unavailable` 结束，不伪造预览或行程。
- 模型 JSON 缺少必需字段：使用既有结构化修正重试；重试耗尽以 `INVALID_DRAFT_SCHEMA` 结束，前端提示重试。
- 实时搜索内容、原始网页正文、令牌、密钥和预签名 URL 不得进入用户日志、审计日志或错误消息。

## 接口边界

前端提交的是已选择目的地的结构化对象，而非用户猜测的行政区划代码：

```json
{
  "destination": {
    "name": "长沙市",
    "display_address": "中国 · 湖南省 · 长沙市",
    "city_code": "430100"
  },
  "start_date": "2026-08-10",
  "end_date": "2026-08-12",
  "preference_tags": ["吃吃喝喝", "citywalk", "历史古建"],
  "prompt": "有老人同行，不想爬山，晚上想逛夜市"
}
```

后端以 `city_code` 作为检索和隔离边界，目的地名称与地址用于展示和审计快照。手动规划和智能规划使用独立 API 操作，避免手动规划引入不必要的 AI 依赖。

## 验收场景

1. 输入“长沙”后看到“长沙市”“长沙县”“长春市”等候选，每项有完整层级地址；选择“长沙市”后，内部城市代码为 `430100`。
2. 未从候选项选择而只输入“长沙”时，智能规划不可提交并显示选择提示。
3. 选择三天、`吃吃喝喝` 与 `citywalk` 后，智能规划创建任务，按已审核资料优先、实时 MCP 兜底处理。
4. 实时来源候选经高德验证后才能进入预览；跨城、重复、无来源和无 POI ID 候选均被剔除。
5. 预览中可区分审核资料与实时网络资料；实时来源不会出现在后续长期 RAG 检索中。
6. 不足两处可验证地点时不创建预览，返回可操作的资料不足提示。
7. 手动规划在 MCP、RAG 或 LLM 不可用时仍可创建日期骨架。
8. 预览确认前行程版本不变；确认后使用版本号和操作 ID 写入，重复确认保持幂等。
9. 非所有者无法读取 generation job、临时 citations、preview 或确认写入。

## 非功能要求

- 目的地搜索必须防抖，且过期请求不得覆盖更新的输入结果。
- 所有联想项与表单控件支持键盘操作和可见焦点。
- 移动端下拉结果、标签和两个规划按钮不得重叠或裁切。
- 实时检索需有任务级限流、超时和候选数量上限，避免单个用户请求无界消耗 MCP 或模型额度。
- 所有新接口均需所有者隔离、明确响应模型、单元测试和 API/Worker 集成测试。
