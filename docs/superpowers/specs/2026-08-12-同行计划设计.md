# 同行计划设计

**状态：** 已完成需求和体验方向确认，待用户审阅后编写实施计划。

## 目标

将现有的结伴请求公告板升级为统一的“同行计划”。用户围绕同一份行程寻找旅行搭子，完成申请、审核、群聊、共同编辑和结束同行的完整闭环。

同行计划覆盖两种出行尺度：

1. 多日旅行：绑定用户已有的完整行程。
2. 短途活动：先创建半天或一天的轻量行程，再进入相同的同行流程。

它们不是三个互相割裂的功能。找旅游搭子、共同改路线和临时出行约伴共享同一套事实、权限、审核、聊天和收尾机制。

## 非目标

- 不新增并行的 `TravelGroup` 或第二套成员、申请、群聊、行程协作实体。
- 不把未接受申请人加入群聊、行程协作者或成员联系方式可见范围。
- 首版不提供实名认证、信用评分、押金、费用分摊、保险、证件信息、住宿安排或违约处罚。
- 首版不支持多人队长、投票式路线审批、候补队列、成员邀请成员或自动结束同行。
- 不公开精确集合点、联系方式、证件、住址、支付信息或私密行程备注。

## 当前差异

当前 `CompanionRequest` 只有标题、城市和描述；页面可申请、撤回、接受、拒绝、关闭和取消，但没有自然的发布入口、日期、人数、预算、偏好、行程绑定、成员管理、直接进群或共同编辑行程体验。

当前可复用基础：

- `CompanionRequest`、`CompanionApplication`、审核状态和 Outbox 事件。
- `TripCollaborator` 的 owner/editor/viewer 行程权限。
- `Conversation`、`ConversationMember` 和 `companion_group` 群聊。
- 行程工作台、版本历史、冲突提示和地点编辑。
- 用户拉黑、举报、通知与管理审核的既有边界。

## 统一模型

保留 `CompanionRequest` 作为同行计划唯一聚合，新增字段：

| 字段 | 类型 | 规则 | 用途 |
| --- | --- | --- | --- |
| `itinerary_id` | UUID FK | 必填 | 关联共同编辑的行程 |
| `trip_kind` | enum | `trip` 或 `activity` | 多日旅行与短途活动显示区分 |
| `start_date` / `end_date` | Date | 从行程版本投影并冻结 | 公开发现和日期筛选 |
| `party_size` | Integer | 最少 2，包含发起人 | 总人数上限 |
| `accepted_count` | Integer | 初始为 1，不能超过 `party_size` | 剩余名额和满员状态 |
| `budget_min` / `budget_max` / `currency` | Decimal/String nullable | 最小值不大于最大值 | 公开预算范围 |
| `travel_pace` | enum | `slow`、`balanced`、`packed` | 匹配节奏 |
| `interest_tags` | JSON list | 最多 8 个受控短标签 | 兴趣筛选与展示 |
| `intro_text` | Text | 必填 | 发起人公开介绍和同行期待 |
| `conversation_id` | UUID FK nullable | 首位成员接受后创建或关联 | 同行群聊事实 |

同行计划业务状态为：

```text
open -> full
     -> closed
     -> cancelled
     -> completed
```

- 审核状态继续独立使用现有 `review_status`：新计划创建时为 `pending_review`，审核通过后为 `approved`。
- 只有 `review_status=approved` 且 `status=open` 的同行计划在公开发现页可申请。
- `full` 表示达到人数上限，停止新申请。
- `closed` 表示发起人关闭招募但不结束已有成员协作。
- `cancelled` 表示发起人在尚未完成同行前取消计划。
- `completed` 表示出行结束，计划、群聊和行程保留为历史，成员行程权限转为只读。

`CompanionApplication` 新增可空 `conversation_id`。申请被接受后写入，供申请人直接进入同行群聊。

## 发布流程

### 多日旅行

1. 行程 owner 或 accepted editor 在工作台点击“发起同行计划”。
2. 系统读取当前选定行程版本，投影目的地、日期和地点概览。
3. 用户填写人数上限、预算、节奏、兴趣标签、公开介绍和同行期待。
4. 服务端创建 `status=open`、`review_status=pending_review` 的同行计划。
5. 管理员审核通过后成为 `open`，进入公开发现页。

### 短途活动

1. 用户在 `/companions` 点击“发布短途活动”。
2. 填写标题、日期、时段、目的地、地点、活动标签、人数和公开说明。
3. 服务端创建半天或一天的轻量 `Itinerary`，并创建 `trip_kind=activity`、`status=open`、`review_status=pending_review` 的同行计划。
4. 审核通过后走与多日旅行完全相同的申请、群聊和协作流程。

发布时必须验证发起人对关联行程拥有编辑权限、行程有至少一个地点、日期有效、人数至少为 2、预算范围合法、标签受控、公开文本完整。客户端不得提交或覆盖服务端生成的行程事实。

### 目的地城市补全

目的地城市码是同行计划公开发现和筛选的内部事实，用户不需要看见或填写行政区划码。

1. 发布多日同行计划时，系统优先从行程创建时保存的目的地和已验证地点的城市信息自动推断城市。
2. 自动推断成功时，发布页显示只读的“目的地城市”摘要，不增加额外输入。
3. 自动推断失败时，发布页显示必填的“目的地城市”搜索选择器。用户选择城市名称，客户端保存受控选项对应的内部城市码。
4. 前端提交 `city_code` 仅作为无法推断时的后备值；后端始终优先采用可信行程事实。
5. 后端既无法从行程推断、又没有收到合法受控城市码时，拒绝发布并返回“请选择目的地城市后再发布同行计划。”
6. 补选城市只补足同行计划的公开发现元数据，不修改原行程的路线、日期或地点。

不接受自由文本城市名作为发布事实。城市选择器必须使用现有目的地搜索/选择能力，保证公开筛选和城市匹配使用有效的内部代码。

## 申请与成员流程

### 公开发现

公开同行计划展示：目的地、日期、类型、已加入人数/上限、预算、节奏、兴趣标签、路线站点数、发起人公开介绍、剩余名额和申请状态。

公开筛选支持目的地、日期范围、`trip_kind`、节奏、标签和剩余名额，并采用稳定游标分页。已满、审核中、已关闭、已结束或已申请状态必须在卡片和详情中明确展示。

### 申请

申请人先阅读公开路线概览、安全提示和同行要求，再填写必填申请说明。申请人可以撤回自己的 `pending` 申请；不能申请自己发起的计划、重复申请、申请已满/关闭/结束/未审核计划，或与发起人/已接受成员存在双向拉黑关系的计划。

### 接受

接受申请在一个事务中执行：

1. 锁定同行计划，并再次验证审核状态、`status=open`、申请仍为 `pending` 且尚未满员。
2. 将申请设为 `accepted`，写入同行群聊 ID。
3. 创建或复用计划的 `companion_group` 会话，将申请人加入有效成员。
4. 创建 `TripCollaborator(role="editor", status="accepted")`。
5. `accepted_count + 1`；达到 `party_size` 时状态改为 `full`。
6. 写入 Outbox 事件，由通知模块通知相关用户。

接受失败时，申请、群聊成员、行程协作者和人数全部回滚，申请保持 `pending`。发起人可拒绝待处理申请。

### 成员管理与退出

所有已接受成员可编辑关联行程：增加/删除地点、调整顺序、调整日程、补充时间和备注。既有行程版本冲突规则继续生效。

只有发起人可：修改计划公开信息、调整人数上限、接受/拒绝申请、关闭招募、移除成员、恢复行程版本、取消或结束同行。

成员主动退出或被发起人移除时：

- 保留其已保存的行程修改和版本历史。
- 撤销其 `TripCollaborator` 编辑权限。
- 标记其同行群聊成员为已离开，阻止后续读写。
- 降低 `accepted_count`；若此前为 `full`，恢复为 `open`，但不会自动接受旧申请。
- 发起人不能移除自己；成员不能主动移除他人。

## 结束同行

发起人选择“结束同行”后：

- 计划进入 `completed`，停止所有新申请和成员加入。
- 群聊保留历史记录，成员不再发送新消息。
- 成员保持同行群聊的有效成员关系以读取历史；聊天服务根据关联同行计划的 `completed` 状态拒绝新的群聊消息。
- 成员的行程权限转为只读；发起人保留自己的编辑权限。
- 共享行程及其版本历史保留。
- 成员可以从自己的可读行程版本另存或创建行程，再发布田野笔记；不自动公开共同路线。

## 页面与交互

### 同行发现页 `/companions`

页面是按出发窗口组织的“共同出行发现页”，不是普通请求列表。

- 顶部提供目的地、日期、类型、节奏、标签、剩余名额筛选。
- 主操作明确分为“发起同行计划”和“发布短途活动”。
- 首条精选内容展示真实行程封面、路线摘要、日期、剩余名额和同行宣言。
- 后续使用路线清单和不同密度图片内容组合；每张卡固定展示旅行可执行信息与申请状态。
- 未登录用户可浏览公开内容，申请时引导登录并保留回跳 URL。

### 同行详情页 `/companions/{request_id}`

- 首屏展示封面、目的地、日期、名额、预算、节奏和标签。
- 展示发起人公开介绍、同行期待和按天路线概览。
- 精确集合点、私密备注、成员联系方式仅对已接受成员显示。
- 申请人看到申请说明表单、剩余名额、安全提示和撤回状态。
- 发起人看到私有申请列表、接受/拒绝、成员管理、人数调整、关闭招募和结束同行。
- 已接受成员看到“进入同行群聊”“打开共同工作台”和退出控制。
- 结束后转为同行回顾，连接保留的行程、群聊和田野笔记发布入口。

### 行程工作台

- 发起人和 accepted editor 可在工作台看到同行计划状态、成员数和进入群聊入口。
- 行程 owner 可发起、关闭或结束同行计划。
- 成员操作造成的版本冲突沿用当前可见冲突提示；不自动覆盖其他人的路线。

## 视觉与动效

同行计划延续 Field / Travel 的“精致旅行编辑部 + 可操作路线档案”语言，但表达共同出行正在形成。

- 使用深海墨蓝 `#102B3A`、雾白 `#F3F7F5`、海玻璃青 `#167A76`、琥珀黄 `#D99824` 和珊瑚红 `#CE644E`。
- 珊瑚红只用于申请同行、发起同行、发布短途活动和进入共同工作台等主要动作。
- 日期、名额、Day 和站点数使用等宽元数据；成员展示使用克制的头像/姓名缩写，不做大型头像墙。
- 路线轨迹、出发日期带和成员状态是主要结构元素；不用装饰性渐变、浮动球、夸张匹配百分比或泛招聘卡片。

动效只绑定真实状态：

- 发现页初次进入时日期带、精选计划和路线记录以 40-70ms 阶梯淡入。
- 筛选结果以透明度和 `transform` 更新，避免突兀跳变。
- 路线章节进入视区时，轨迹线逐段延伸，地点依次点亮。
- 申请提交、成员加入、人数变化、权限获得、成员退出和计划结束使用 160-320ms 的状态转换。
- 不使用循环漂浮、弹跳、粒子、闪烁或假的成功动效。
- 所有动效使用 `opacity` 和 `transform`，不动画布局属性。
- `prefers-reduced-motion` 下移除位移动画，保留可理解的即时状态更新。

## 安全与隐私

首版安全闭环：

- 申请说明必填。
- 公开同行计划、申请和成员关系可举报。
- 已存在的拉黑关系在申请、接受、建群和加入行程时双向检查。
- 发起人可移除成员；成员可主动退出。
- 加入前展示线下见面安全提示：选择公开场所、独立安排行程与住宿、不向陌生人转账。
- 联系方式和精确集合地点在未接受前不可见。
- 所有公开同行计划都经过管理员审核。

社区模块不直接写通知；所有申请、接受、拒绝、撤回、成员退出/移除、满员、结束同行状态变化写入 Outbox，由通知模块消费。公开同行计划不得自动进入官方知识域；如进入社区经验 RAG，仍需单独知识审核，且不能证明高风险实时旅行事实。

## API 契约

| 接口 | 权限 | 行为 |
| --- | --- | --- |
| `GET /companion-requests` | 公开 | 游标分页发现已审核 `open` 同行计划；支持目的地、日期、类型、节奏、标签和名额筛选。 |
| `GET /companion-requests/{id}` | 公开/成员 | 返回公开详情；仅成员获得群聊、成员和受保护路线信息。 |
| `POST /itineraries/{id}/companion-requests` | owner/editor | 从已有行程版本创建审核中同行计划。 |
| `POST /companion-requests:activity` | 消费者 | 创建轻量行程和审核中短途活动同行计划。 |
| `PATCH /companion-requests/{id}` | 发起人 | 修改公开信息、人数、偏好及招募状态。 |
| `POST /companion-requests/{id}/applications` | 消费者 | 提交必填申请说明。 |
| `POST /companion-applications/{id}:accept` | 发起人 | 原子接受、建群/入群、授予行程编辑权、计数和满员处理。 |
| `POST /companion-applications/{id}:reject` | 发起人 | 拒绝待处理申请。 |
| `POST /companion-applications/{id}:withdraw` | 申请人 | 撤回待处理申请。 |
| `DELETE /companion-requests/{id}/members/{user_id}` | 发起人 | 移除已接受成员并撤销行程/群聊访问。 |
| `POST /companion-requests/{id}:leave` | 已接受成员 | 主动退出，保留历史行程修改。 |
| `POST /companion-requests/{id}:complete` | 发起人 | 结束同行，成员转只读，群聊保留历史。 |
| `GET /companion-requests/mine` | 消费者 | 返回用户发起、已加入和待处理申请的同行计划。 |

## 错误和一致性

| 场景 | 结果 |
| --- | --- |
| 无行程编辑权、行程为空或日期非法 | 拒绝发布同行计划，不创建半成品请求。 |
| 行程无法推断目的地城市且未选择有效城市 | 拒绝发布，提示选择目的地城市；不修改原行程。 |
| 满员、关闭、已结束、未审核 | 拒绝申请。 |
| 重复申请、自己申请自己、已被拉黑 | 返回具体业务错误，不泄露拉黑细节。 |
| 接受时状态/名额变化 | 事务内重新校验后返回冲突，不创建群聊或协作者。 |
| 成员退出/被移除后访问群聊或工作台 | 按成员权限返回不可访问，不泄露受保护内容。 |
| 结束后编辑/申请 | 返回计划已结束，并保留历史路线和群聊可读状态。 |

## 测试与验收

### 后端

- 行程 owner/editor 才能从非空行程创建同行计划。
- 发布页优先显示自动识别的目的地城市；无法识别时必须选择受控城市名称，前端不展示行政区划码。
- 后端优先使用可信行程城市事实，只把合法受控 `city_code` 作为无法推断时的后备值。
- 轻量活动创建行程和同行计划必须原子成功或失败。
- 未审核、关闭、满员、结束、重复、自申请和拉黑场景不能申请。
- 接受申请在单一事务中创建群聊成员、行程 editor、计数和申请状态；失败必须回滚。
- 满员后停止申请；成员退出/移除恢复开放名额；历史版本修改保留。
- 移除、退出、结束同行撤销未来行程编辑和群聊读写权。
- 结束同行保留成员的群聊历史读取，但聊天服务拒绝该同行群聊的新消息。
- Outbox 事件不直接创建通知，审核和社区知识边界保持完整。
- 新模型字段附带 Alembic revision，并验证升级、降级一版、再次升级。

### 前端

- 发现页筛选、分页、加载、空、错误、已满与已申请状态清晰可用。
- 多日旅行和短途活动都能完成发布和审核前状态展示。
- 详情页按当前用户身份显示正确的申请、管理、成员、群聊和共同工作台动作。
- 申请、接受、退出、被移除、结束同行后的页面状态与后端事实同步。
- 桌面和移动端不裁切日期、名额、申请栏、路线、成员或底部行动栏；键盘焦点和减少动态设置有效。

### 浏览器验收

1. 创建多日行程，从工作台提交同行计划并完成审核。
   对缺少城市信息的既有行程，确认发布页要求选择目的地城市，补选后可提交，且原行程未被改写。
2. 创建一日短途活动并完成审核。
3. 未登录用户浏览和筛选；登录后提交带说明的申请。
4. 发起人接受申请，确认申请人直接进入同行群聊并成为行程 editor。
5. 双方编辑路线，确认版本冲突提示和历史版本均正常。
6. 达到人数上限，确认公开申请按钮变为已满。
7. 成员退出或被移除，确认其历史修改保留但群聊/编辑权限被撤销。
8. 发起人结束同行，确认成员只读、群聊历史保留，并可进入后续田野笔记发布流程。
