# 群聊与实时消息设计

## 目标

将同行计划的沟通体验收敛为以群聊为中心的流程：没有成员时不创建用户可见群聊；第一个申请人被发起人接受时创建正式群聊；铃铛只提醒群聊未读消息；在线成员通过 WebSocket 实时收到新消息。

## 产品规则

- 同行计划发布和管理员审核不创建群聊。
- 第一个申请人被接受时，发起人必须填写群聊名称并上传群头像。
- 群聊名称和群头像任一缺失，接受操作失败，申请保持待处理。
- 创建群聊后，发起人和第一个成员自动加入，申请人的行程编辑权限按现有规则授予。
- 第三个及后续申请仍由发起人审核；接受后加入现有群聊，不重复创建群聊。
- 计划满员、关闭、取消或完成后禁止新的申请。
- “申请已通过”等状态流水不在铃铛中单独展示。
- 铃铛只展示有未读消息的群聊、群名和未读数量。
- 点击铃铛进入群聊列表；点击群聊进入聊天并将该群消息标记为已读。
- 在线聊天消息必须在持久化提交成功后通过 WebSocket 推送；断线后通过重新连接和历史接口补齐消息。

## 数据与接口

- `Conversation` 持久化群名和群头像媒体 ID，并与同行计划建立唯一关联。
- 首次接受申请接口接收群名和头像媒体 ID，在同一事务中创建会话、成员关系和申请接受结果。
- 后续接受申请接口只增加会话成员，不允许修改既有群资料。
- 群聊未读摘要按用户和会话聚合，响应包含会话 ID、群名、群头像、未读数和最后一条消息摘要。
- WebSocket 使用现有一次性实时票据和会话成员校验，不在 URL 中传访问令牌。
- REST 发送消息成功提交后发布会话消息事件；WebSocket 广播失败不回滚已持久化消息。

## 前端交互

- 第一次接受申请打开群资料表单，群名和图片均为必填项。
- 群主详情页展示现有群资料和待处理申请。
- 申请通过通知不再作为独立通知卡片生成。
- 顶部铃铛显示群聊未读总数，展开或跳转后按群显示未读数量。
- 聊天页面建立 WebSocket，收到消息后按消息 ID 去重并立即追加；重连后刷新历史。
- 设置入口保持顶部“个人中心与设置”文字入口和移动端导航入口。

## 验收标准

- 无申请人时数据库不存在用户可见同行群聊。
- 接受第一个申请时缺少群名或头像会被阻止，且不会创建半成品群聊。
- 填写群名和头像后，发起人和申请人都能在群聊列表看到同一群。
- 接受后续申请不会创建第二个群聊。
- 铃铛不显示“申请已通过”等独立流水，只显示群聊未读聚合。
- 两个已登录浏览器分别打开同一群聊，一个发送消息，另一个无需刷新即可看到。
- WebSocket 断开后重连，期间消息通过历史接口补齐且不重复。
