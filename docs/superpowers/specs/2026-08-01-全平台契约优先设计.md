# AI Travel Platform Full-Scope Contract-First Design

> Date: 2026-08-01
> Status: Approved for specification review
> Scope: All capabilities in `docs/AI旅行平台需求文档.md`

## 1. Goal

Build every capability in the travel-platform PRD through contract-driven, module-based parallel development. Product priority labels do not decide whether a capability is built. They are replaced by a full feature inventory and a technical dependency order.

The delivery model is:

```text
Frozen contracts -> shared platform -> paired frontend/backend module work
-> continuous integration -> real-service end-to-end verification
```

The platform uses real MySQL, Redis, Elasticsearch, RabbitMQ, OSS, AMap, Qwen, and other configured third-party services. Missing credentials must produce an explicit unavailable state; no module may fabricate a successful external result.

## 2. Architecture

The system remains a modular monolith with two Vue applications and an independent asynchronous worker.

```text
Vue 3 consumer application       Vue 3 admin application
             \                         /
              \------ HTTPS/API -------/
                          |
                     FastAPI API
                          |
       +------------------+------------------+
       |                  |                  |
  domain modules     AI orchestration    realtime delivery
       |                  |                  |
       +------------------+------------------+
                          |
       MySQL  Redis  RabbitMQ  Elasticsearch  OSS
                          |
                    async worker
```

### 2.1 Deployment units

- `frontend-c`: Vue 3/Vite consumer PC application.
- `frontend-b`: Vue 3/Vite admin and provider PC application.
- `api`: FastAPI REST, SSE, WebSocket ticketing, authentication, and authorization.
- `worker`: asynchronous generation, import, route recalculation, export, narration, indexing, and notification work.
- `mysql`: business fact source.
- `redis`: cache, rate limits, short-lived state, presence, and session-related data.
- `rabbitmq`: durable domain-event delivery, retries, and dead-letter queues.
- `elasticsearch`: public itinerary and community search only.
- `oss`: private media, exports, credentials, and generated audio storage.
- `nginx`: HTTPS, static application delivery, and reverse proxying.

### 2.2 Ownership and dependency rules

- MySQL is the only business fact source. Redis, RabbitMQ, Elasticsearch, and OSS never become the authoritative state of a business aggregate.
- A module owns its tables, migrations, services, routes, schemas, and tests.
- Modules communicate through published application-service interfaces or Outbox-backed domain events. A module must not write another module's private table.
- AI agents can call only allowlisted integration tools and return Pydantic-validated structured results. They cannot write the database or change orders, payments, membership, or authorization directly.
- Third-party SDK usage is isolated under `integrations/`; domain modules depend on integration interfaces rather than vendor SDKs.

## 3. Canonical Contracts

The documents `docs/AI旅行平台需求文档.md`, `docs/API设计.md`, `docs/数据库设计.md`, `docs/技术设计.md`, and `docs/前端交互规范.md` must be reconciled into one contract set before module implementation starts.

### 3.1 Naming decisions

The following names are canonical for all new API, database, frontend, and test work:

| Concept | Canonical name |
|---|---|
| Travel plan API and aggregate | `itineraries` |
| Itinerary date | `itinerary_days` |
| Itinerary POI item | `itinerary_events` |
| Itinerary history | `itinerary_versions` |
| AI generation task | `generation_jobs` |
| Import task | `import_jobs` |
| Export task | `export_tasks` |
| Supply search task | `travel_search_jobs` |
| Supply search candidate | `travel_offers` |
| Travel pre-order | `travel_orders` |
| Payment audit record | `payment_records` |

`/trips` is not a new API route. Existing PRD references to `/trips` must be reconciled to `/itineraries`.

### 3.2 API conventions

- All APIs use the `/api/v1` prefix.
- API paths use plural nouns and kebab-case; JSON fields use snake_case.
- Public IDs are UUID strings. Timestamps are UTC RFC 3339. Local itinerary dates use `YYYY-MM-DD`.
- Monetary values are decimal strings with a three-character ISO currency.
- List APIs use opaque cursor pagination.
- Async APIs return a resource ID, status, progress, and a stable error code when failed.
- Create-task, import, export, order, payment, and refund writes require `Idempotency-Key`.
- Itinerary structure writes require `If-Match-Version`; collaborative itinerary writes also require `X-Operation-ID`.
- Every response must include or expose a request identifier. Errors use `code`, `message`, `request_id`, and optional `details`.

### 3.3 State rules

Each resource owns its own state machine. Cross-resource changes happen through a transactional application service and, where needed, a reliable Outbox event.

| Resource | Canonical states |
|---|---|
| Itinerary | `draft`, `ready`, `archived` |
| Generation job | `queued`, `understanding`, `searching_poi`, `routing`, `planning`, `validating`, `succeeded`, `failed`, `cancelled` |
| Import job | `queued`, `parsing`, `awaiting_confirmation`, `matching_poi`, `succeeded`, `failed`, `expired`, `cancelled` |
| Export task | `queued`, `running`, `succeeded`, `failed`, `expired`, `cancelled` |
| Community post | `draft`, `pending_review`, `published`, `hidden`, `rejected` |
| Travel order | `PENDING_CONFIRMATION`, `PAYING`, `PAID_PENDING_FULFILLMENT`, `CONFIRMED`, `FAILED`, `REFUNDING`, `REFUNDED`, `CLOSED` |
| Payment record | `pending`, `paying`, `paid`, `failed`, `refunding`, `refunded` |
| Supply confirmation | `pending_confirmation`, `confirming`, `confirmed`, `failed`, `not_supported` |

Travel-order responses always include `status`, `payment_status`, and `fulfillment_status`. Neither frontend nor backend consumers may infer one from another.

### 3.4 Core domain invariants

- Every itinerary event has a verified AMap POI ID or explicitly user-confirmed coordinates. AI text alone cannot create an itinerary event.
- Ordinary itinerary edits retain the user's event order. Route optimization and natural-language adjustments produce a preview and require user confirmation before writing a version.
- Restoring an itinerary creates a new version; history is never overwritten.
- Anonymous visitors can only read published content and valid link-visible itineraries. Copying, saving, editing, importing, collaborating, chatting, and ordering require authentication.
- Payment callbacks are server-verified for signature, order number, and amount, and are idempotent. A browser payment result cannot change an order to paid.
- Supply searches return genuine results, explicit empty results, or failure. The system never fabricates prices, inventory, booking, or fulfillment.

## 4. Parallel Development Model

The contract and architecture role owns shared contract documents, shared schemas, enums, error codes, event definitions, and permission matrices. Domain teams consume frozen contracts and request contract changes instead of changing them independently.

| Team | Backend ownership | Frontend ownership | Dependencies |
|---|---|---|---|
| Platform | configuration, DB, auth, JWT, RBAC, errors, rate limits, realtime tickets | application shells, routing, auth state, shared API client | none |
| Itinerary intelligence | itineraries, AI, maps, imports, route calculations, collaboration, export | planner, itinerary list, workspace, map, import, versions, collaboration | platform |
| Community communication | posts, reactions, comments, reports, companions, chat, notifications | community feed, post views, companion flow, chat, notifications | platform, public itinerary copy |
| Travel commerce | supply search, offers, pre-orders, payments, refunds | search, offer list, order and payment states | platform |
| Guide and trip support | checklist, budget, guide sessions, narration, sources, TTS | checklist, budget, guide player | itinerary intelligence, maps, media |
| Provider and monetization | attractions, providers, experiences, sessions, bookings, verification, commission, membership, entitlements, itinerary packages | experiences, packages, membership, provider workspace | platform, commerce, itineraries |
| Admin operations | management queries, moderation, audit, index and queue operations | dashboard, user/content/order/task/search/configuration management | all domain contracts |
| Integration and quality | migration order, seed data, Worker, Outbox, Compose, contract and integration tests | end-to-end tests and browser acceptance | all teams |

### 4.1 File ownership

- Only the platform team modifies shared core initialization, base configuration, Compose, `.env.example`, and common API-client infrastructure.
- Domain teams modify only their backend module, assigned frontend feature directory, assigned migrations, and tests.
- Only the integration team modifies cross-module registration, seed orchestration, end-to-end fixtures, and full-stack environment wiring.
- Contract changes require a documented change request and must update API, data, event, frontend-state, and test contracts together.

### 4.2 Technical integration order

All functionality is in scope. This order controls dependency integration, not product inclusion:

1. Platform runtime, configuration, authentication, database access, migrations, and both application shells.
2. AI itinerary generation with real AMap POIs and map rendering.
3. Itinerary editing, route recalculation, optimization, versions, imports, collaboration, and export.
4. Community publication, itinerary copying, companion requests, chat, and notifications.
5. Supply search, offers, pre-orders, Alipay sandbox payment, refunds, and travel-order states.
6. Checklist, budget, image recognition, guide sessions, narration, TTS, and playback.
7. Attractions, providers, experiences, sessions, reservations, verification, commission ledger, membership, and itinerary packages.
8. Complete admin workflows for user, content, provider, order, task, search, queue, and configuration operations.
9. Full real-service acceptance, fault injection, authorization regression, and cross-module bug correction.

## 5. Configuration and External Integrations

Root `.env` contains local real connection values and secrets. It is ignored by version control. Root `.env.example` contains all keys, permitted formats, non-secret examples, and enablement switches.

```text
APP_*
MYSQL_*
REDIS_*
RABBITMQ_*
ELASTICSEARCH_*
JWT_*
AMAP_*
DASHSCOPE_*
COSYVOICE_*
ALIYUN_OSS_*
ALIYUN_SMS_*
ALIPAY_*
WECHAT_*
SUPPLIER_*
CORS_*
```

Integration behavior:

- AMap: separate browser JS and server Web Service credentials. Verify POI, routing, geocoding, weather, and map behavior with actual responses.
- Qwen and Qwen-VL: validate structured outputs before persistence. Expose timeouts, malformed output, and unavailable-service errors explicitly.
- CosyVoice: store generated audio in OSS, associate it with a narration version, and cache reusable results.
- OSS: use short-lived upload/download credentials and private object ownership checks.
- SMS: enforce rate limits and verification TTL. Fixed test codes require an explicit development-only configuration.
- WeChat OAuth: use one-time Redis state values and HTTPS callback validation.
- Alipay: use sandbox credentials, verified callbacks, active payment queries, idempotency, and refund handling.
- Supplier integrations: display only authorized real results. A missing integration returns empty or unavailable states, never synthetic fulfillment.

## 6. Reliability, Security, and Testing

### 6.1 Reliability

- Business transactions write both state changes and `outbox_events` in the same MySQL transaction.
- Publishers use RabbitMQ confirms before recording events as delivered.
- Consumers deduplicate via `event_id` or a domain-specific unique key.
- Retry queues use bounded attempts and dead-letter routing. Admin replay does not mutate the original event body.
- All external calls use connection, read, and total timeouts with bounded retries.
- Worker restarts must resume pending Outbox work or leave tasks in an explicit retryable or failed state.

### 6.2 Security and privacy

- Keys are only loaded by backend environment configuration, never shipped to frontend bundles.
- Refresh tokens are stored only as hashes; browser refresh tokens use secure HTTP-only cookies.
- WebSocket connections use short-lived single-use realtime tickets and recheck resource access after connection.
- All B-end actions verify audience, role, resource ownership, and provider scope where applicable.
- Public itineraries remove contact details, precise lodging addresses, and chat content.
- Logs redact phone numbers, tokens, OpenIDs, payment data, user locations, and full chat or prompt bodies.

### 6.3 Module entry gate

Before integration, a module must provide:

1. Contract-aligned models, Alembic migrations, schemas, routes, services, error codes, and tests.
2. Frontend features using the shared real API client; temporary mocks must be derived from the same frozen schema.
3. A real-service smoke test once credentials are configured.
4. Tests for success, authorization failure, an idempotency or state conflict, and third-party timeout/unavailability.
5. UI states for loading, empty, no access, error, retry, and connection recovery.
6. A contract test verifying frontend/backend field names, enums, money, and timestamp formats.

### 6.4 Final acceptance

The final environment must demonstrate:

- Both Vue applications, API, Worker, and all infrastructure start against the supplied configuration.
- Every PRD feature maps to an API, table ownership, visible UI entry point, and acceptance test.
- Authentication and role boundaries are enforced server-side.
- AMap POIs, routes, and map rendering use real data.
- Payments, supply searches, and guide generation report real outcomes and do not fake successful fulfillment.
- Collaboration, chat, payments, exports, and domain events are idempotent and recover safely after retries or restarts.
- Automated unit, integration, contract, fault, permission, and browser end-to-end suites are repeatable.
