# 分域 RAG 与受控多智能体行程编排 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the shared travel retrieval path and serial itinerary workflow with isolated official, community, and user-memory retrieval domains plus a controlled multi-agent itinerary preview pipeline.

**Architecture:** Keep RabbitMQ Worker and LangGraph as the only asynchronous execution and orchestration mechanisms. Add domain-aware RAG adapters and a retrieval agent that returns an evidence package, then model Planning, Memory Retrieval, Map, and Generation Review as typed dependencies invoked by the planning graph; every result is persisted as a redacted audit entry with the immutable preview.

**Tech Stack:** Python 3.11, FastAPI, SQLAlchemy 2, Alembic/MySQL, asyncpg/PostgreSQL, LangGraph, httpx, OpenAI-compatible embeddings, Zilliz Milvus, Elasticsearch 8, RabbitMQ.

## Global Constraints

- LangGraph remains the only Agent state machine; specialized Agents return typed results and never autonomously delegate.
- The Planning Agent may create only immutable AI previews. `ItineraryService` remains the sole writer of confirmed MySQL itineraries.
- Public official, public community, and private user-memory data use separate Milvus collections and Elasticsearch indexes. A query must explicitly declare its domain.
- User memory is read only when `user_id` is supplied and enforced in both dense and BM25 filters. No chat, preview, confirmed itinerary, or model inference automatically creates a memory.
- Official RAG, final POI verification, and generation review are required. Community retrieval, memory retrieval, and route estimation may degrade only with a durable audit flag.
- A review result may cause at most two automatic revisions. Missing trusted official evidence, POI city mismatch, memory access denial, and unresolved evidence conflicts never enter the revision loop.
- Consumer-visible progress contains only product stages. Prompts, model reasoning, full evidence payloads, and private memory contents never appear in consumer APIs or admin summaries.
- Use additive Alembic revisions; verify each MySQL schema change with upgrade, downgrade one revision, and upgrade again.

```python
class KnowledgeDomain(StrEnum):
    OFFICIAL = "official"
    COMMUNITY = "community"
    USER_MEMORY = "user_memory"


class AuthorityLevel(StrEnum):
    OFFICIAL = "official"
    COMMUNITY = "community"
    MEMORY = "memory"


@dataclass(frozen=True)
class RagQuery:
    query: str
    city_code: str | None
    domains: tuple[KnowledgeDomain, ...]
    user_id: str | None = None

    def __post_init__(self) -> None:
        if not self.query.strip() or not self.domains:
            raise ValueError("query and domains are required")
        if KnowledgeDomain.USER_MEMORY in self.domains and not self.user_id:
            raise ValueError("user_id is required for user-memory retrieval")

    @property
    def visibility(self) -> str:
        return "private" if self.domains == (KnowledgeDomain.USER_MEMORY,) else "public"
```
