## Parallel Dispatch Waves

### Wave 0: Contract and foundation

Dispatch the contract/platform team first. It owns the shared documents, core runtime, configuration, migrations, auth, application shells, API client, and Outbox primitives. No other team changes these shared files.

### Wave 1: Independent domain scaffolding

After foundation contracts and core APIs pass, dispatch itinerary intelligence, community communication, travel commerce, and admin operations. Admin may only build shell/read-client portions until each domain provides its read contract.

### Wave 2: Dependent capabilities

After itinerary intelligence and commerce module gates pass, dispatch guide/trip support and provider/membership. The provider team reuses travel commerce payment APIs; it does not introduce another callback implementation.

### Wave 3: Continuous integration and release

The integration/quality team starts after foundation and continuously integrates completed module gates. It owns full-stack wiring and returns defects to the responsible module team with a regression case.

## Completion Requirement

A team hands off only after its plan's module gate passes: migration, unit/API tests, permission test, idempotency or conflict test, external-unavailable test, frontend typecheck/build, and contract test. The integration team does not waive these gates.
