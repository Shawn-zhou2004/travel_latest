# 实时交通 MCP 与模拟出票 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add Magic MCP-backed real-time train and flight offers to the existing order flow, with server-side Offer snapshots, Alipay sandbox payment, post-payment revalidation, and clearly labeled mock ticket issuance.

**Architecture:** Extend the existing supplier search contract with `train`, transport metadata, and revalidation. A server-only MCP provider creates immutable MySQL offers; the existing order/payment/Outbox/Worker chain invokes a mock fulfillment adapter only after successful revalidation. The consumer UI becomes a train/flight search and purchase flow without direct MCP access.

**Tech Stack:** Python 3.11, FastAPI, SQLAlchemy 2, Alembic/MySQL, RabbitMQ Worker, httpx MCP client, Alipay sandbox, Vue 3, TypeScript, Element Plus.

## Global Constraints

- MCP is queried only by backend providers; browser clients never receive MCP URLs, tool names, keys, or raw responses.
- Offers are immutable, user-owned, short lived, and never enter RAG.
- Payment success is not ticket issuance. Worker revalidation and mock fulfillment determine issuance.
- Full passenger ID numbers are request-only and cannot enter database, logs, Outbox, RAG, agent audits, or browser persistence.
- Seat selection is a preference only; mock fulfillment assigns a clearly simulated seat.
- MCP query failure creates no offer, order, or payment; post-payment revalidation failure is retryable and never issues a ticket.
- A price/availability/class mismatch after payment produces ticket-failed-awaiting-refund state and enables full sandbox refund.
