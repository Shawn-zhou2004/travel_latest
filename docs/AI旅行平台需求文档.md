# AI 旅行平台需求文档

> 契约状态：全平台产品能力清单
> 共享术语与权限：`docs/contracts/`

## 产品目标

平台帮助旅行者创建和编辑基于真实 POI 的行程，依据可信旅行资料完成规划、协作、发布和相关购买。平台面向消费者用户、服务商员工和平台管理员，提供两个 Vue PC 应用，并由 FastAPI 模块化单体和异步 Worker 支撑。

以下能力均属于产品范围。技术依赖图只规定集成顺序，不代表交付排除。外部集成只能返回真实结果、明确的空结果或不可用状态；平台不得伪造 POI、价格、库存、支付、预订、出票或履约事实。

## 用户与规则

| 用户 | 产品角色 |
| --- | --- |
| 匿名访客 | 仅可阅读已发布内容和具有有效链接可见性的行程。 |
| 消费者用户 | 在授权资源内创建、拥有、分享、导入、导出、发布、聊天、搜索和下单。 |
| 行程协作者 | 按被授予的角色读取或编辑一条已接受协作的行程。 |
| 服务商员工 | 仅运营被分配的服务商、景点、体验、场次、预约和服务商订单资源。 |
| 平台管理员 | 运营带审计的用户、内容、服务商、订单、任务、队列、搜索、知识和配置流程。 |

强制访问规则见 `docs/contracts/权限矩阵.md`。链接可见性只授予读取权限。行程编辑始终保留用户事件顺序，除非用户确认优化或自然语言调整预览。每个行程事件都必须有已验证的高德 POI ID，或明确由用户确认的坐标。

## 状态与信任规则

- 规范资源名称和状态枚举定义于 `docs/contracts/说明.md`。
- 旅行订单读模型始终独立提供 `status`、`payment_status` 和 `fulfillment_status`。
- 支付回调必须由服务端校验签名、商户订单号和金额，并保持幂等；浏览器支付结果不能将订单设为已支付。
- MySQL 是业务事实来源；Redis、RabbitMQ、Elasticsearch 和对象存储都不是权威聚合状态。
- AI Agent 只能使用白名单工具和经验证的结构化输出，不能直接写数据库，也不能修改授权、订单、支付、会员或审核状态。
- 已发布行程必须去除联系方式、精确住宿地址和聊天内容。

## AI 知识与智能体需求

- 行程规划使用受控专业 Agent：规划、检索、用户记忆检索、地图验证和生成审核。规划 Agent 是唯一协调者；专业 Agent 通过结构化结果协作，不会自主委派工作。
- AI 只能创建带审计的不可变行程预览。旅行者必须确认指定预览后，现有行程服务才可执行版本化业务写入。
- 生成审核最多允许两次自动修订。缺少可信官方证据、POI 未验证或城市不一致、私有记忆越权、证据冲突无法消解时，必须返回澄清、无结果或不可用状态。
- 平台维护独立的官方旅行知识、公开社区经验和用户私有记忆三个知识域。每次检索必须显式选择允许的域；私有记忆始终要求当前用户身份且不得共享。
- 官方知识的权威级别高于社区经验。社区内容可辅助灵感和体验建议，但不能单独确立当前价格、营业时间、路线或票务库存等高风险事实。
- 长期记忆由用户明确控制。只有用户主动新增、编辑或确认的记忆可以保留；普通对话、浏览记录、AI 推断、行程预览和确认行程都不会自动形成记忆。
- 面向旅行者的 AI 只显示简明进度、引用、地点验证、预算结论和待确认事项；不得显示模型推理、内部 Prompt、Agent 对话、完整证据包或其他用户数据。

## 网页知识治理

- 只有平台管理员可发起网页知识发现。首期消费者问答和行程生成不直接执行联网网页搜索。
- 网页搜索结果只是候选资料，不是旅行事实。平台保存来源元数据和有限摘要后，必须经过自动安全检查和管理员人工决定，才可进入官方或社区知识域。
- 候选资料保留标题、来源 URL 与域名、摘要、发布日期、抓取时间、查询词、目标城市、目标知识域和内容哈希。平台不保存完整原始网页，也不保存外部 Provider 凭据。
- 政府、景区、地图服务和受授权供应商官方站点，经审核后可获得较高权威等级；一般旅行媒体和攻略只能成为社区经验级资料。

## 交通查询与演示购买

- 用户可按出发地、目的地、出发日期和乘客数量查询火车与航班。服务端获取并标准化实时 Provider 结果为短时 Offer；前端不得直接连接外部交通 Provider。
- 行程推荐可携带出发地、目的地和日期跳转至交通搜索页面。进入购票流程时必须重新查询最新 Offer，不得将早前规划建议视为可预订库存。
- 交通 Offer 展示车次或航班号、出发到达信息、时长、可选席别/舱位、价格、余量、有效期和退改规则。实时价格、库存、席别可用性和航班状态属于交易快照，不是 RAG 知识。
- 旅行者选择席别或舱位，并选择靠窗、靠过道或无偏好。座位偏好不是锁座承诺；演示票券中的模拟出票结果才是本次演示的最终状态。
- 乘客结算允许提交一次性乘客资料。完整证件号只用于请求处理，不得保存至平台存储、日志、事件、AI 记录、知识库或浏览器持久化；订单只保留脱敏乘客信息。
- 支付宝沙箱支付成功仅表示收款确认，随后才启动履约。Worker 必须复核已选 Offer；若价格、余量或席别变化，订单进入“出票失败待退款”，不得伪造票券。
- 首期在支付成功且复核通过后生成明确标记的火车或航班模拟票券。真实锁座、出票、退改签、退款和乘客实名管理属于后续受授权铁路、航司、OTA 或 GDS 供应商集成。
- 实时交通查询不可用时，平台不创建 Offer、订单或支付记录，并向旅行者提供重试状态。支付后的二次校验临时不可用时，履约可重试，但不得出票。

## 验收预期

每项能力都必须对应 API、所属持久化、可见 UI 入口、权限规则、必要的下游领域事件和自动化验收覆盖。模块必须处理成功、授权拒绝、幂等或冲突、外部超时和不可用情况。消费者端和管理端必须提供加载、空状态、无权限、错误、重试和连接恢复状态。

AI 验收还必须覆盖知识域隔离、引用权威等级、用户记忆隔离、两次修订上限、最终 POI 验证和不可变预览审计。网页知识验收必须确认未审核候选不会进入任何知识域。交通验收必须确认客户端不能伪造 Offer、完整乘客证件号不会持久化、支付由服务端验签、模拟出票前必经支付后二次校验，且出票失败保持可退款而不显示为已确认票券。
