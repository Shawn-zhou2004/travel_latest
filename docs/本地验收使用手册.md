# 当前项目使用手册

更新时间：2026-08-12

本文面向本地开发和验收人员，说明当前项目的启动顺序、访问入口、登录方式、核心操作、依赖检查和常见故障处理。它不包含任何数据库密码、第三方密钥、支付私钥或生产凭据。

## 0. 开始前：运行架构与启动顺序

当前开发环境由两台机器组成：

- Windows 开发机运行 FastAPI、消费者端 Vite、管理端 Vite 和异步 Worker。
- CentOS 7 虚拟机 `192.168.142.50` 运行 MySQL、Redis、RabbitMQ、Elasticsearch 和 MinIO 等基础设施。
- 根目录 `.env` 保存连接配置和密钥，已被 Git 忽略。不要提交、截图或在日志中输出它的内容。

每次开发或验收前，在 Windows PowerShell 检查基础设施连通性：

```powershell
Test-NetConnection 192.168.142.50 -Port 3306
Test-NetConnection 192.168.142.50 -Port 6379
Test-NetConnection 192.168.142.50 -Port 5672
Test-NetConnection 192.168.142.50 -Port 9200
Invoke-RestMethod http://192.168.142.50:9200/_cluster/health
```

四个端口必须为 `True`。Elasticsearch 健康接口应返回 `green` 或开发期可接受的 `yellow`。其中 `9200` 不可用时，AI runtime 无法初始化，智能规划和 AI 对话会失败，但手动规划、普通行程编辑等不依赖 AI 的功能仍可使用。

按以下顺序启动 Windows 服务。每条命令使用独立的 PowerShell 窗口：

```powershell
# 终端 1：API
cd backend
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000
```

```powershell
# 终端 2：异步 Worker
cd backend
.\.venv\Scripts\python.exe -m app.workers.main --check-config
.\.venv\Scripts\python.exe -m app.workers.main
```

```powershell
# 终端 3：消费者端
cd frontend-c
npm run dev
```

```powershell
# 终端 4：管理端
cd frontend-b
npm run dev -- --port 5174
```

启动后先访问 `http://127.0.0.1:8000/api/v1/health`。返回 `200` 后再打开前端页面。Worker 启动后会向 Redis 写入心跳；管理员可在 `/ai` 页面查看其状态。

当前不要在 Windows 项目根目录直接执行 `docker compose up -d`。本项目的开发基础设施运行在 VM 中，Windows 再起一套 Docker 基础设施会导致端口和数据环境混乱。

## 1. 访问地址

| 应用 | 地址 | 用途 |
| --- | --- | --- |
| 消费者端 | `http://127.0.0.1:5173` | 行程、AI、社区、订单、体验、会员等消费者功能 |
| 管理端与服务商工作台 | `http://127.0.0.1:5174` | 平台管理、服务商体验与预订核销 |
| API 健康检查 | `http://127.0.0.1:8000/api/v1/health` | 确认 API 可用，预期返回 `200` |
| OpenAPI 文档 | `http://127.0.0.1:8000/docs` | 查询 API 请求与响应契约 |

当前本地服务：

- API：`127.0.0.1:8000`
- 消费者端：`127.0.0.1:5173`
- 管理端：`127.0.0.1:5174`
- MinIO S3 API：`http://192.168.142.50:9000`
- MinIO readiness：`http://192.168.142.50:9000/minio/health/ready`

公网演示需要单独启动 cpolar 或其他 HTTPS 隧道。临时公网域名会变化，旧地址返回 `404` 时通常表示隧道已停止或被回收，而不是 API 业务接口失效。每次更换域名后，需要同时更新 `.env` 中的 `CORS_ORIGINS`、前端 Vite 的 `allowedHosts`，然后重启 API 和对应 Vite 服务。不要将临时域名当作固定生产地址。

## 2. 开发登录

消费者端和管理端都使用手机号验证码登录。

1. 打开相应登录页。
2. 输入符合中国手机号格式的 11 位手机号。
3. 点击“Get code”或“获取验证码”。
4. 当前开发环境会显示 `Development code: xxxxxx`。
5. 输入该六码验证码并登录。

开发验证码仅用于本地环境，不是短信服务上线状态。当前手机号是否获得管理员或服务商权限，取决于该用户已有的角色和 provider scope。

登录后请注意：

- 消费者端只能使用消费者会话。
- 管理端的 `platform_admin` 会话可进入平台运营页面。
- 服务商会话必须同时具备 `provider_admin` 或 `provider_staff` 角色，以及至少一个 provider scope。
- 未满足权限时页面会显示无权限或空状态；不要通过修改浏览器请求绕过服务端授权。

## 3. 消费者端验收

### 3.1 个人资料与私有头像

入口：导航栏个人资料，或 `http://127.0.0.1:5173/me/profile`。

可验收操作：

1. 修改昵称并保存，页面提示“Profile saved.”。
2. 选择 JPEG、PNG 或 WebP 图片，文件不得超过 10 MiB。
3. 等待“Avatar saved.”提示。
4. 刷新页面，确认头像仍显示。

预期边界：

- 图片先通过预签名 PUT 上传至私有 MinIO bucket，再由 API 以 ETag 完成确认。
- 头像下载 URL 为短期签名 URL，只在当前页面内存中使用。
- 不允许把其他用户的 asset ID 写入个人资料。

### 3.2 行程与路线

入口：导航栏“My plans”，或 `http://127.0.0.1:5173/itineraries`。

可验收操作：

1. 从“New itinerary”进入 `/plan` 创建 AI 行程，或使用已有开发行程。
2. 在行程工作区点击“加入第一天”，再搜索高德 POI 并加入当天。
3. 调整地点顺序、更新备注、删除地点或新增日期。
4. 对有多个地点的一天触发路线重算，观察 `queued`、`calculating`、`completed` 或 `failed` 状态。
5. 打开历史版本，确认版本号递增且旧版本不被改写。

预期边界：

- 行程结构写入使用 `If-Match-Version` 与 `X-Operation-ID`，旧版本会返回冲突而不是覆盖新数据。
- 每个地点必须由服务端高德 POI 验证。
- 只有 owner 或已接受的 editor 能修改；viewer 只能读取。
- 非所有者直接访问私有行程 URL 时，应看到“这份行程暂时不可访问”，不应看到编辑、导出或分享控件。

### 3.2.1 删除行程与日期

使用 owner、已接受 editor 和无权限用户准备一条至少两天的行程；另准备一条关联同行计划的行程。

1. 以 owner 打开“我的行程”或行程工作区，点击“删除计划”，阅读永久删除警告后点击确认。行程应从列表移除；工作区删除后应回到 `/itineraries`。请求不需要标题输入或请求体。
2. 以 accepted editor 和无权限用户尝试删除整个行程。两者都不得看到可用的删除计划操作；直接请求时应返回 `403 FORBIDDEN`。不存在的行程返回 `404 ITINERARY_NOT_FOUND`。
3. 为行程创建状态分别为 `open`、`full`、`closed` 的同行计划后尝试删除。每种状态均应返回 `409 COMPANION_PLAN_ACTIVE`，页面提示先结束或取消同行计划，且工作区保持打开、行程数据不变。`cancelled` 或 `completed` 的同行计划不应触发此保护。
4. 以 owner 或 accepted editor 删除某一天，确认当天的地点、路线分段和路线计算任务消失，其余日期按 `0` 起连续排序，且行程版本递增。删除后日期仍存在时，行程起止日期应按剩余日期重算。
5. 删除最后一天，确认行程仍存在并显示空工作区；原有 `start_date` 与 `end_date` 不得改变。重复使用同一个操作 ID 提交删除时，应返回相同的幂等结果，不得再创建版本或删除其他日期。
6. 以旧的 `If-Match-Version` 删除日期，确认返回 `VERSION_CONFLICT` 和服务器当前快照，页面刷新或进入既有冲突处理，不能静默重试或覆盖新内容。
7. 在桌面和窄屏移动视口执行计划和日期删除。确认弹窗警告和取消/确认控件不被遮挡；用键盘 Tab 能到达删除控件与弹窗按钮，焦点清晰可见，Esc 或取消不会删除内容。

### 3.3 新建行程：目的地、手动规划与智能规划

入口：导航栏“My plans”中的“New itinerary”，或 `http://127.0.0.1:5173/plan`。

按以下顺序验收：

1. 输入“长沙”，确认可选择“长沙市”，并显示完整地址“中国 · 湖南省 · 长沙市”。
2. 只输入“长沙”但不从结果中选择，尝试“手动规划”和“智能规划”；两种操作都应被阻止并提示选择搜索结果。
3. 选择目的地，设置 `2026-08-10` 至 `2026-08-12`，再选择不超过三个偏好标签；第四个标签不得被接受。
4. 停止 AI、RAG、MCP 和 Worker 相关服务后执行“手动规划”；应进入行程工作区，并显示三天日期，每天的地点列表为空。手动规划不应创建 generation job。
5. 在已审核知识可覆盖目标城市时执行“智能规划”；观察任务经过 `retrieving_reviewed_sources`、`verifying_pois`、`planning`、`validating` 等安全阶段，preview 应显示来源引用，确认后才写入行程。
6. 在已审核知识不足、MCP 可用时执行“智能规划”；观察 `searching_live_sources` 阶段，preview 中实时来源应标注“本次实时网络资料”或等价的 live-web 标签。
7. 构造任意一天少于两个已验证地点的条件；任务应以 `no_result` 结束，说明可靠地点不足，且不得创建或写入行程。
8. 使用第二个消费者账号尝试读取第一个账号的任务、preview 和引用；服务端应拒绝访问，页面不得显示地点或来源内容。

预期边界：

- 智能规划先检索已审核知识；仅当已审核且已验证的地点不足以覆盖每天两个地点时，才允许任务内实时 MCP 回退。
- 行程规划的实时 MCP 仍只使用任务内的受控来源元数据，不自动索引或写入长期知识。对话助手是独立链路：官方 RAG 无可信答案时，先用用户原问题搜索，再对最多五个高排名 HTTPS 结果调用 fetch MCP；robots 拒绝、不可读和重复正文会被过滤，剩余正文限长切片后仅用于当前回答，不自动写入 Milvus、Elasticsearch 或长期知识表。
- 不论来源类型，每个写入 preview 的地点都必须有引用，并经高德验证 POI ID、目标城市归属和坐标。
- `no_result` 表示可用的已验证地点不足，不等同于 MCP、高德或其他依赖不可用。

### 3.4 分享与协作

入口：行程工作区右上角“Share itinerary”。

可验收操作：

1. 创建分享链接，确认只在创建时返回完整链接。
2. 用无登录浏览器窗口打开链接，确认只能读取公开的分享视图。
3. 邀请已有用户成为 `viewer` 或 `editor`。
4. 受邀用户通过邀请链接接受协作。
5. 验证 viewer 无法编辑，editor 可编辑但仍受版本冲突保护。

当前建议额外验收：撤销分享链接后再次访问应不可用；若页面未提供撤销入口，可通过 API 文档确认对应接口状态。

### 3.5 AI 行程与对话

入口：`http://127.0.0.1:5173/assistant`。

可验收操作：

1. 直接输入自然语言旅行问题，不输入城市代码。观察“检索已审核资料”的流式状态、逐段显示的回答和来源引用。
2. 对官方资料未覆盖的目的地提问。确认状态切换到网络搜索，回答带 `live_web` 来源；系统会对最多 3 个 HTTPS 搜索结果使用 fetch MCP 补充正文事实，且不会自动写入知识库。
3. 在回答生成期间刷新页面或模拟断线后重新进入对话，确认最终消息只保存一次。
4. 在“用对话修改已有行程”选择一个至少含一个地点的行程。
5. 输入修改要求并生成预览。
6. 确认 preview 显示地点、日期和引用后再点击确认。
7. 打开更新后的行程，确认创建了新版本。

### 3.7 管理员新增三亚官方景点资料

入口：`http://localhost:5174/ai`，点击“新增官方资料”。

1. 资料类型选择“验证 POI 说明”。
2. 三亚城市代码填写 `460200`。
3. 每个景点单独新增一条资料，并填写对应的高德 POI ID。
4. 标题使用明确的景点名，例如“天涯海角景区详细游览信息”。
5. 正文至少填写景点特色、推荐游览内容、适合人群、建议游览时长和注意事项；不要只填写景点名称。
6. 提交后在“知识资料”中找到 `pending_review` 记录，检查城市、POI、正文和来源边界。
7. 点击“审核并索引”，等待状态变成 `indexed`。
8. 在管理端使用“检索验证”搜索“天涯海角适合怎么玩”，确认返回详细正文片段。
9. 在消费者端新建对话提问“天涯海角适合怎么玩”，确认回答包含景点特色和游览建议，并显示官方引用。

推荐正文结构：景点概览、主要看点、推荐路线或游览顺序、适合人群、建议时长、季节与天气提示、门票/预约/开放时间的官方信息边界、交通提示和更新时间。

### 3.6 路线天数与导出

1. 在路线规划页左侧选择一个日期后加入新的一天。日期可以早于或晚于原始范围，行程的开始或结束日期会随之更新。
2. 点击导出图标，选择一个历史版本，生成 DOCX 并等待任务到达 `succeeded` 后下载。
3. 导出文件应使用独立的 exports bucket；生成失败时界面显示任务错误，可重试，不应提供下载链接。

预期边界：

- 空行程会返回 `TARGET_ITINERARY_EMPTY`，不会创建 preview 或新版本。
- AI 只生成不可变 preview，用户确认后才写入行程。
- 如果 preview 基于旧行程版本，确认会返回 `VERSION_CONFLICT`。
- 相同操作 ID 的确认重试必须返回幂等结果，不创建重复版本。
- 当某个日期原本未安排活动时，修改 preview 会保留该空日期，不伪造地点。
- 若模型遗漏活动必需的 `poi_id` 或标题，任务会以 `INVALID_DRAFT_SCHEMA` 失败并提示重试；这不是“没有可靠结果”。

### 3.6 导出

入口：行程工作区“导出 DOCX”。

可验收操作：

1. 选择一个历史版本创建导出任务。
2. 观察任务状态从排队到成功或失败。
3. 成功后获取短期下载链接并下载 DOCX。
4. 对失败任务使用重试入口，确认只允许失败或取消任务重试。

当前边界：导出使用任务创建时保存的不可变版本快照，不能把当前行程内容混入旧任务。

### 3.7 田野笔记、同行计划、聊天与通知

入口：消费者导航栏的“田野笔记”“同行计划”“Messages”“Notifications”。

可验收操作：

1. 使用 owner 或已接受 editor 创建一条有两个日期、已排序 POI 和备注的行程；在工作区选择一个保存版本，填写标题和 recap，上传 JPEG、PNG 或 WebP 图片并选择封面，提交田野笔记。
2. 使用平台管理员在 `/content/posts` 找到类型为“田野笔记”、路线快照为“已附加”的待审核记录；确认能看到标题、作者 ID、状态和处理理由，但看不到原行程、快照 JSON、复制行程 ID 或媒体预签名 URL。
3. 管理员以明确理由通过笔记。确认其进入已发布状态；outbox 中应有 `post.published`，payload 仅含 `post_id`、`author_id`、`content_type:"itinerary"` 和 `city_code`。如有城市代码，社区知识审核是独立的待审核记录，不能把通过内容审核当作已进入 RAG。
4. 在未登录窗口打开 `/community` 和已发布笔记详情；待审核、已拒绝和已隐藏笔记不得公开读取或复制。
5. 用另一消费者账号在已发布笔记下评论、点赞、收藏，再调用复制操作一次。使用相同的 `Idempotency-Key` 重试，必须返回同一 itinerary ID，且源笔记 `copy_count` 不得再次增加。
6. 编辑复制得到的行程，确认源行程和公开笔记的冻结快照均不变化，原作者不会成为复制行程协作者。
7. 使用 owner 或 accepted editor 从含至少一个地点的当前行程版本发布同行计划，填写 2--12 人容量、节奏、兴趣标签和公开介绍；或以已验证 POI 发布同日短途活动。两种计划均应显示为 `open`/`pending_review`，公开列表不可见。
8. 管理员在 `/content/companions` 审核计划。列表和详情仅应显示类型、目的地、日期、人数、节奏、标签、公开介绍、业务状态、审核状态和理由；不得显示路线快照、群聊、消息、成员、申请内容、联系方式或拉黑关系。通过后，且业务状态为 `open` 的计划才进入公开发现。
9. 准备两个独立浏览器会话：窗口 A 登录 owner，窗口 B 登录 applicant；不要在两个窗口复用同一访问令牌或本地存储。owner 对应一条管理员已通过、`status=open`、`accepted_count=1`、`conversation_id=null` 且至少还有一个名额的计划；applicant 尚未申请该计划。
10. 窗口 B 打开 `/companions/{request_id}`，确认只能看到公开路线概览，然后提交 1--1,000 个非空白字符的申请说明。窗口 A 刷新同一详情并看到该 `pending` 申请；此时两个账号的 `/messages` 都不得出现新群聊，铃铛也不得出现“申请已通过”流水。
11. 窗口 A 首次点击接受。在群资料弹窗中先分别尝试缺少群名、缺少头像，确认不能提交或接口返回 `GROUP_NAME_REQUIRED`/`GROUP_AVATAR_REQUIRED`，申请仍为 `pending`、`accepted_count` 仍为 1、`conversation_id` 仍为空。随后填写唯一群名并上传已完成的 JPEG、PNG 或 WebP 群头像再接受；响应必须包含同一个非空 `conversation_id`、`group_name`、`group_avatar_asset_id`、`accepted_count=2`，窗口 A 和 B 的 `/messages/{conversation_id}` 均显示相同群名和头像。
12. 在窗口 B 请求该 `group_avatar_asset_id` 的 `/api/v1/media/{asset_id}/download-url` 应成功；用不在群内的账号请求同一路径应为 `404 MEDIA_ASSET_NOT_FOUND`。成员退出或被移除后再次请求也应为相同 404，且不能凭群成员身份下载 owner 的其他私有媒体。
13. 保持窗口 A、B 同时打开 `/messages/{conversation_id}`。窗口 B 发送唯一文本，必须先收到 REST `201`，窗口 A 随后无需刷新即通过 `message.created` 显示；窗口 A 回复时窗口 B 同样即时显示。断开再恢复 API 或浏览器网络后，客户端必须使用新实时票据重连并补拉 HTTP 历史，消息 ID 不重复，发送失败的消息不会被误标为已送达。
14. 让窗口 A 停留在群外，窗口 B 再发一条消息。窗口 A 的铃铛数字只增加该群的未读数；打开 `/notifications` 只显示该群、头像、最后消息和聚合数量，不显示 `companion_application.accepted`/“申请已通过”行。窗口 A 打开 `/messages/{conversation_id}` 后再次读取 `/api/v1/notifications/summary`，该群消失且 `total_unread` 相应归零。
15. 验收后续接受时，另建隔离的 applicant-2 测试账号申请同一未满计划。窗口 A 接受时不得再次要求群名或头像；响应的 `conversation_id`、`group_name` 和 `group_avatar_asset_id` 必须与首次接受完全相同，数据库中仍只有一个群聊，新成员获得 editor 和活动群成员资格。接受至人数上限后计划变为 `full`，新申请被拒绝。
16. owner 移除成员或成员主动退出。确认历史行程修改仍保留，成员的未来行程编辑、群聊读写和群头像下载被撤销；若此前满员，人数递减且计划回到 `open`。owner 不能移除或退出自己。
17. owner 完成同行。确认计划为 `completed`，非 owner 的行程 editor 权限被撤销；保留成员能读取历史群聊但发送新消息返回 `COMPANION_PLAN_COMPLETED`。已完成、已取消或已拒绝的计划不可重新招募或申请。
18. 检查 Outbox 和通知消费者：申请、接受、拒绝、撤回、移除、退出、满员及完成均由 Outbox 交给通知模块；社区事务本身不得直接写入通知行。接受事件行可保留作内部审计，但用户铃铛和 `/notifications` 页面只消费 `/notifications/summary` 的群聊未读聚合。

当前边界：田野笔记只能从服务端冻结的选定行程版本创建，不能通过通用帖子接口伪造快照；公开快照不包含预算、清单、协作者、分享令牌、操作历史、路线任务、持久化 day/event ID、支付数据或未选择媒体。同行计划不支持身份认证、押金或分摊付款、候补、多人 owner 或自动结束；管理员只审核，不得绕过 owner 的成员和生命周期规则。HTTP 历史读取和权限是消息事实来源；WebSocket 只负责提交后的即时提示，Redis 不可用时已提交消息仍须通过重连后的 HTTP 历史恢复。

### 3.8.1 会员购买与 AI 额度

准备两个隔离的消费者浏览器会话 A、B，以及一个 `platform_admin` 管理端会话。支付回调需要按《支付宝沙箱联调说明》配置可从公网访问的 API 和消费者端 HTTPS 地址；全程不得记录密钥、签名、完整回调表单或沙箱账号密码。

1. 管理员打开 `/memberships/plans`，创建或确认一个计划：已发布、`purchasable=true`、币种 `CNY`、价格 `19.90`、有效期 `30` 天、行程生成额度 `10`、AI 对话额度 `300`。草稿或已归档计划不得在消费者端可购买；未发布计划不能设为可售。
2. 会话 A 打开 `http://127.0.0.1:5173/memberships`。确认卡片显示服务端的 `¥19.90 / 30 天`、`10 次行程生成`、`300 次 AI 对话`。浏览器请求体只能提交 `membership_plan_id`，不得包含金额、周期或额度。
3. 点击一次“立即购买”。确认购买创建为 `pending_payment/pending/pending`，随后进入本站 `/memberships/pay/{purchase_id}` 页面。页面应本地显示二维码、`CNY 19.90` 和十分钟倒计时，浏览器不应跳转或请求支付宝收银台页面资源。按钮处于处理中时再次点击不得创建第二笔购买或支付。
4. 保持二维码页面可见，确认它每三秒调用本服务的支付查询；切换标签页后轮询停止，重新切回后立即查询一次。用支付宝沙箱 App 扫码并完成付款，确认 API 公网回调返回纯文本 `success`，支付页无需浏览器刷新即显示服务端确认的付款/授权状态。
5. 让未付款二维码过期，确认页面停止轮询并只显示“重新生成二维码”。点击后必须使用同一购买创建新支付尝试和支付单号，旧二维码不再显示；页面不得自动生成新二维码。支付完成后进入“我的权益”，确认购买为 `paid/paid/authorized`，显示 `paid_at`、`authorized_at`、有效期与正确的会员额度。管理端 `/memberships/purchases` 只显示脱敏购买审计事实，不能显示支付单号、签名、原始回调或支付渠道交易号。
6. 使用会话 B 或无会员的新用户：完整智能规划可成功一次，第二次在同一 UTC 自然月必须返回/显示 `AI_QUOTA_EXHAUSTED`、剩余为 `0`、下次重置时间和升级入口；AI 助手在同月第 21 条有效消息前后同样验证免费 `20` 次边界。无效请求或上游不可用失败不应消耗额度。
7. 使用会话 A：先确认余额接口或“我的权益”显示会员周期余额，再分别完成 10 次完整智能规划和 300 次有效 AI 助手消息的边界验收。会员有效期内优先扣会员额度，免费额度不应被消耗；第 11 次规划或第 301 条消息应显示 `AI_QUOTA_EXHAUSTED`，且会员额度耗尽时不把免费额度作为回退。
8. 会话 A 在首个会员仍有效时再次购买相同计划并完成沙箱付款。第二笔授权必须立即生效：`valid_from` 为支付确认时刻且早于第一笔 `valid_until`，新额度立即可用；第一笔额度周期和第二笔额度周期均保留，不能覆盖原购买快照，且 AI 额度扣减在两个周期同时生效时优先使用 `period_end` 更晚的周期。
9. 让支付宝重发同一笔成功回调，或在受控测试环境重放同一份已验证回调。响应仍为 `success`，但购买有效期、会员记录、额度周期及 `membership.entitlement_updated` Outbox 事件数量均不得再次增加。
10. 受控制造“已支付但未授权”状态后，管理员在购买审计页执行一次“重试开通”。仅已支付且未授权购买允许操作；成功后变为 `authorized`。已授权、未支付或不存在购买应被拒绝，且普通消费者不能调用管理接口。

预期边界：支付成功只能由已验签异步回调或服务端主动查询确认。本地二维码、倒计时和浏览器状态均不是支付成功证明；重新登录后可再次打开购买二维码页或在“我的权益”刷新查询。会员购买不进入旅行订单、供应商履约、出票或核销流程，也没有用户自助退款。

## 8. 常见问题

### API 或页面打不开

1. 先访问 `http://127.0.0.1:8000/api/v1/health`。
2. 若不是 `200`，确认 API 进程是否正在监听 `8000`。
3. 确认消费者端 `5173`、管理端 `5174` 的 Vite 服务仍在运行。

### AI 一直排队或生成失败

1. 在管理端 `/ai` 检查 Worker heartbeat。
2. 在 Windows 执行 `Test-NetConnection 192.168.142.50 -Port 9200`，再执行 `Invoke-RestMethod http://192.168.142.50:9200/_cluster/health`。
3. 若 `9200` 不通，在 CentOS 以 `es` 用户进入 `/usr/local/es/elasticsearch-8.14.3` 并运行 `./bin/elasticsearch`；另开终端确认 `curl http://127.0.0.1:9200/_cluster/health` 成功。
4. Elasticsearch 恢复后重新创建或重试智能规划任务。`AI_DEPENDENCY_UNAVAILABLE` 表示运行依赖不可用，不表示目的地没有合适地点。
5. 检查目标城市是否存在已审核、已索引的公开知识；知识不足时才会尝试 MCP 实时来源回退。
6. 记录 generation job ID、状态和错误码，不要记录用户 prompt、令牌或预签名 URL。

### 页面出现 `401 Unauthorized`

1. 返回登录页，重新获取开发验证码并登录。访问令牌过期或浏览器清理了会话时，受保护接口会返回 `401`。
2. 在浏览器开发者工具的 Network 面板确认失败请求的实际路径。`/auth/me` 失败通常是会话问题；`/generation-jobs`、preview 或行程接口失败还应检查当前用户是否为资源所有者。
3. 通过 cpolar 访问时，确认请求 Origin 是当前公网域名，且该域名已加入 `CORS_ORIGINS`。浏览器翻译插件可能报出 `translate-pa.googleapis.com` 的 CORS 错误，这不是本项目 API 错误。

### 公网 cpolar 地址返回 `404` 或浏览器报 CORS

1. 在 Windows 先确认本地健康检查 `http://127.0.0.1:8000/api/v1/health` 为 `200`。
2. 查看 cpolar 当前输出中的 `Forwarding` 地址；不要复用旧的临时地址。
3. 使用新的 HTTPS 域名更新 `.env` 的 `CORS_ORIGINS` 和前端 Vite `allowedHosts`，重启 API、消费者端和管理端。
4. 对需要 API 调用的公网消费者页面，应分别建立消费者端和 API 的 HTTPS 映射；不要把页面地址误当作 API 地址。

### 头像或导出下载失败

1. 检查 MinIO readiness URL 是否返回 `200`。
2. 确认上传完成后返回 ETag，且 asset 仍归当前用户所有。
3. 下载 URL 是短期签名 URL，过期后应重新从 API 获取，而不是复用旧链接。

### 服务商没有看到核销预订

1. 确认后台会话具备 `provider_admin` 或 `provider_staff` 角色。
2. 确认已选择与预订所属体验一致的 provider scope。
3. 只有 `reserved` 状态预订出现在待核销列表；已核销、取消或其他状态不会显示。
